* **Are they equals?** Yes — your question is right to flag the earlier wording. **CORRECTED**: `pwRcd` and `pwDbg` are **equals for main** — either unlocks `window.GoogleUblock` log level 1, and **neither depends on the other** (no `if dbg requires rcd`). Past bug you hit was `if (dbg) else if (rcd)` skipping `rcd` side-effects when `dbg` fired — fixed with independent flags, no else:
  ```

  // each input evaluated independently
  //  if (h==HASH_DBG) dbgOK=true;
  //  if (h==HASH_RCD) rcdOK=true;
  //  mainOK = dbgOK || rcdOK
  //  // no else — both branches run, both side-effects fire if both true
  ```
  Your `pwView/pwAK/pwRes` **do work when `pwDbg` is used** — they check `mainOK` (either), not `rcdOK` alone. The earlier "dependency on `pwRcd` but never on `pwDbg`" meant **don't make `pwDbg` require `pwRcd`** (dbg stays independent). `pwView/pwAK/pwRes` require *main* (level 1), so either `rcd` **or** `dbg` satisfies them at level 1. The only difference is log level elevation.
* **Log level is `会員`-gated, not just password (per your spec):**
  ```
  // 会員 is the existing header var (0/1/2) — already in bundle
  if (会員==0) level=0 regardless of dbgOK/rcdOK; // always level 0
  else if (会員==1) level = mainOK ? 1 : 0;        // dbg or rcd → 1, dbg doesn't give 2 at 会員=1

  // level 0 = silent / deflection, 1 = standard ledger/queue, 2 = verbose + queued/flush/refresh pool
  ```
  So: `会員=0` → 0 regardless; `会員=2 + rcd` → 1; `会員=1 + dbg` → still 1; **only** `会員=2 + dbg` → 2.
* **In-built for `pwView/pwAK/pwRes`**: they are *level-1* operations (`view log level 2 / queued items / flush / refresh pool`), so they check `level>=1` (`mainOK && 会員!=0`), not `rcdOK` alone. No `FNV(rcd+":"+pw)` derivation that would tie them to rcd only — instead `hash = FNV(mainSalt + ":" + pw)` where `mainSalt` is `seed-lib` common for both, or simply independent hashes gated by `level`.
