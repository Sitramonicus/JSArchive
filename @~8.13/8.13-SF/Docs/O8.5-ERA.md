# O.8.5-S4 — Build Plan (2026-09-09)

Scope decisions + roadmap from the seamless/technique/memory/telemetry discussion.

## 0. Locked decisions

1. **Source-first (the long way) for everything structural.** The gist artifact gets
   surgical patches only (password swap already done: `builds/O8.5-current-obf-edit.js`,
   sha `b9e5ff2b...`). Memory layout, decoy-string camo, lexicon mechanics, engine
   choice: all applied on the clean core, then regenerated -> sharded -> obfuscated.
2. **Marker/password scheme:** KEEP 佐藤 結衣 as the searchable marker in the UNOBFUSCATED
   shard/clean line. In the obfuscated result of THAT shard only, 佐藤 結衣 remains
   searchable and replaceable with the canonical phrase (search -> replace -> works).
   The digest stays pinned to the canonical phrase (already true: digest ==
   sha256(salt + canonical), verified). Non-OTO changes applied well before the OTO phase.
3. **Engine:** the USER obfuscates via obfuscator.io (their pipeline), NOT via the
   javascript-obfuscator npm scripts (OTO). OTO scripts still provided as alternates.
   Whole-file uniform seam removal + transport compression run on the USER'S resulting
   artifact (their bundle), after they supply it.
3. **Camo scope:** zero-width (ZWJ/ZWNJ in identifiers, FEFF as inter-token whitespace,
   zw chars inside strings) + RLO in DECOY-ONLY strings, per-instance random via the
   generator's seed RNG. No esoteric full encodings (JSFuck-style expansion blows the
   2-3 MB soft / 5 MB hard paste cap; see below). No fake telemetry.
4. **Memory posture:** encoded-at-rest everywhere (existing band-rot) + per-call
   transient decode + zero retention of decoded tables. No ArrayBuffer "linear heap"
   refactor unless user opts in (item B4).
5. **Engine:** whole-file uniform javascript-obfuscator last-mile pass (verdict from
   seamless trial). Optional js-confuser variant per instance for heterogeneity.
6. **Transport compression** (gzip/deflate/brotli + b64 + ~425 B self-extract shell)
   available at ship time; proven end-to-end.

## 1. Why the "lazy way" (edit the gist artifact) is a dead end for most items

| Change | On obfuscated gist artifact | On clean source -> rebuild |
|---|---|---|
| Password / marker swap | OK (surgical string swap; done) | n/a |
| ZWJ identifier camo | NO (no AST, 1-line, identifier occurrences unsafe to regex) | YES (generator emits; survives rename only as post-pass) |
| RLO/zw inside decoy strings | RISKY (can't tell which strings are inert in obf output) | YES (whitelist known inert decoys) |
| FEFF whitespace sprinkle | MAYBE (token-level insert is safe; but adds to artifact we replace anyway) | YES (post-obf micro-pass) |
| Memory hygiene / pool refactor | NO (structural refactor) | YES |
| Lexicon / phrase rotation | NO | YES |
| Engine rotation | n/a (already obfuscated) | YES |

Rule: anything that touches HOW the code is written goes through the clean line.

## 2. Memory techniques — honest verdicts (vs. the pasted AI pitch)

The pitch's native-level verdicts are right; its three "YES" rows are oversold:
- **ArrayBuffer/typed arrays are NOT invisible.** Chrome heap snapshots list typed
  arrays and their backing stores; DevTools memory inspector reads them; page-level
  JS (or Puppeteer) can read them if it can reach the instance. They change the
  *shape* (one big blob vs. many named strings) but not the *exposure*.
- **"Instantly unreachable ... young-gen sweep" is not a guarantee.** GC timing is
  not script-controllable; a snapshot taken during the decode window still catches
  cleartext. Transient windows only *shrink* exposure.
- **Wasm memory is not an "opaque black box."** DevTools has a wasm memory
  inspector; Puppeteer can read exported memory; heap/linear-memory dumps include it.
  It only moves bytes outside the JS GC heap.
- **The real kernel:** keep sensitive text OUT of V8's *string* heap — encoded at
  rest, decoded near use, never retained. That is already S3's design (band-rot
  lexicon, KC=47/KP=61, decode at log fire). The gap audit (B4) closes the leftovers
  (routes table, phrase literal) without a rewrite.

| Technique | Verdict (revised) |
|---|---|
| TypedArray "linear heap" | PARTIAL — shape change only; heavy refactor; skip unless B4 audit shows a real gap |
| Transient closure isolation | HYGIENE only — shorter windows, no guarantees; already practiced |
| Wasm memory isolation | NO — false black-box claim; cost/complexity not justified for a console paste |

## 3. Whitespace/esoteric languages — rejected on size math

Full JSFuck-style encoding expands source ~7-20x. Our smallest viable product is
~192 KB clean / ~256 KB obfuscated -> JSFuck would land 3-10+ MB: over the 5 MB hard
cap, before adding the shard variety. Whitespace-language-with-interpreter is worse.
Transport compression instead: 192 KB -> ~37 KB paste (brotli-11), 698 KB gist ->
~330 KB, comfortably under the soft limit.

## 4. Roadmap

### Phase A — clean-core changes (o8cmp, generator line)
- A1. Canonical phrase at the unlock call site in the generator template (removes
  the 佐藤 search-replace need; see decision #2).
- A2. Decoy-string camo: generator emits per-instance N inert strings (N drawn from
  seed RNG) carrying RLO/PDF pairs and zw chars; whitelist = generator's own decoy
  blocks ONLY. Zero functional/printing strings touched.
- A3. Zero-width identifier option: post-obf micro-pass that renames a seeded subset
  of generated identifiers with ZWJ tails (or js-confuser zeroWidth generator when
  the jsc variant is used). Deterministic, validated by battery.
- A4. FEFF sprinkle micro-pass (post-obf, token-boundary inserts) — cosmetic only.
- B-phase memory & transport items below.

### Phase B — memory + telemetry hygiene (the "under-thought" gaps)
- B1. Transport audit: confirm every outbound call rides the app's own request layer
  (native headers/X-Super-Properties/UA/key order), payloads byte-shape identical to
  real client calls, cadence disciplines as documented. Produce
  `TRANSPORT_SHAPE.md` checklist (no fake presence, no new origins, fail-closed URL
  guard already in O8.3).
- B2. Retention scan: assert no decoded lexicon/phrase table outlives its call
  (code-anchor + runtime check).
- B3. Route table & residual plaintext sweep: extend band-rot coverage to any
  leftover readable strings the audit finds (S3 did codenames+phrases; check
  routes, URLs, labels).
- B4. OPTIONAL (user pick): move large static pools into a Uint8Array backing store
  behind the existing decode layer (shape change only; validation cost ~1 battery).
- B5. Explicitly non-goals (recorded): no active anti-CDP/anti-debugger,
  no timing-fingerprint countermeasures, no heartbeat/presence spoofing.

### Phase C — regenerate + validate (mirrors Shard-3 pipeline)
core -> generator (fresh seed, suite O.8.5-S4) -> lexenc -> shardify -> strip
(comment-free) -> battery: harness-default consumer + unlocked, L1/L0, unlock-unit
with canonical phrase, negative gate, duplicate-paste guard, stress
multi/midrun/srvdone/blip, MC readout, determinism byte-exact x2, residue scans
(zero old phrase, zero plaintext tells, zero comments).

### Phase D — last mile + packaging
- D1. Whole-file uniform obfuscation (obfuscate-final.js, seed-pinned) -> seam-free
  single-line product.
- D2. Optional second variant with js-confuser (heterogeneity evidence).
- D3. Release bundle (payload + 6 pieces + stitcher + README + SHA256SUMS), mirror
  O8.5-Shard-3.zip layout; plus optional compressed self-extract delivery
  (<~100 KB paste) if wanted.
- D4. Record + docs: O8.5-S4_RECORD.md, CURRENT_STATE.md update, CHEATSHEET
  appendix (phrase/digest/marker scheme), CHANGELOG.md row O.8.5-S4 (existing
  format), OBFUSCATION_TECHNIQUES.md additions (zw/RLO camo, memory-hygiene,
  transport-shape invariants, engine rotation).

## Architecture lesson (recorded in SHARD2_PIPELINE.md)

The generator does region surgery (decode cut/re-emit, decoy strip/re-emit, head
banner rewrite). Feeding it a pre-sharded template silently merged wrappers and
broke scope (observed `Log is not defined` in engine). Canonical flow is therefore
**generate first (single scope), shard the instance afterwards** at top-level
statement seams; the only safe seams are depth-1 boundaries because the engine is
one closure. Legacy flags & guard (`_0xrunKey` early return) ride inside the engine
wrapper so duplicate-paste protection still aborts the whole run.

## Decoder reference (record-only; not for the cheat sheet)

dec = rot over [0x20,0x7E]: c' = 0x20 + (((c-0x20-k) % 0x5F) + 0x5F) % 0x5F for c<0x80,
else unchanged. KC=47 (codename words), KP=61 (phrase texts). Sites call
`_0xlex.C(i)` / `_0xlex.P(i, arr)` unchanged; phrase arrays decode per element at
call time via `_0xlex.d("…")`.

## V1 — Global symbol leak (`Symbol.for("quest-suite:o8:active")`) — ⚠️ PARTIALLY VALID → MODIFY

**Claim check (true parts):** the run-lock uses `Symbol.for("quest-suite:o8:active")` — confirmed in source. `Symbol.for` registers in the global symbol registry, and the symbol is set as a `window` key (`window[_0xrunKey] = _0xrunOwner`), so `Object.getOwnPropertySymbols(window)` plus `String(sym)` would surface the semantic string `quest-suite:o8:active` and the owner object. That is a real, greppable footprint — modest in practice (nothing in our code or the client's observable surface is known to enumerate window symbols), but cheap to fix.

**Why their fix is wrong:** replacing `Symbol.for(...)` with a local `Symbol(...)` **breaks the duplicate-paste guard**: a second paste of the same file would create a *different* symbol and never see the first run's marker → two runs on one page. The registry semantics are load-bearing (same artifact must always derive the same key).

**Disposition — MODIFY (fold into O8.5 base):** keep `Symbol.for` but make the description a **neutral, per-instance opaque token with no semantic words**, e.g. `Symbol.for("_0xq" + <instance token>)`, emitted by the generator so each suite's artifact carries its own meaningless key. Dedupe preserved; semantic grep surface gone. (Optional extra: also de-word the warn text — keep as-is is fine.)

## V2 — "Dead" auxiliary telemetry arrays — ❌ PREMISE WEAK → REJECT both fixes

**Claim check:** the `generated auxiliary region` exists — it is the **decoy noise block** (Tier A/B/C), deliberately inert, in place since O8.2-Juggler-7 by design and user mandate ("decoy/herring reversible + marked"; it is marked `self-contained` and never touches real logic). The claimed anomaly is hypothetical; no evidence any anti-automation system memory-scans a page's JS heap for strings.

**Their two fixes are both worse:**
- *Remove it:* contradicts the user-approved decoy/anti-DRY layer and lowers analysis cost asymmetry for zero measured benefit.
- *Activate it to send dummy `/api/v9/science` events* through the internal HTTP client on 2–5 min intervals: **violates the standing no-new-network / no-new-timers constraint** and is the highest-risk suggestion in the report — fabricating events into Discord's real science pipeline is exactly the "infiltrative, high-risk state spoofing" we do not do; server-side event correlation would see invented payloads from a real session token; new periodic timers contradict our runtime-loop catalog ("activity cannot be hidden; it can only be not-created").

## V5 — Hook descriptor leakage — ⚠️ MOSTLY ALREADY MITIGATED → ACCEPT as verified, no real change needed

**Claim check (against actual hook code):** the hook already:
- fails closed on frozen/sealed targets (`Object.isFrozen`/`isSealed` guard);
- captures the **own** descriptor, walks the prototype chain for the original, and builds replacement flags mirroring the original: `{ writable: !!d.writable, configurable: !!d.configurable, enumerable: !!d.enumerable }` — i.e. **it does not widen configurability** in the normal path (their worry);
- installs via `Object.defineProperty(obj, key, { value: fn, ...flags })`;
- restores by **exact original descriptor re-apply** (`Object.defineProperty(obj, key, own)`) or delete when no own descriptor existed;
- spoofs `toString`/`length`/`name` via a Proxy `get` trap and reports a pristine `Function.prototype.toString` descriptor through the `getOwnPropertyDescriptor` trap.

So the claimed leak (hook making a non-configurable original configurable) does **not** occur on the standard path. Their proposed patch is roughly equivalent to existing behavior (and has its own flaw: deriving flags with `!== false` can widen `writable` on accessor-originals). `Reflect.defineProperty` vs `Object.defineProperty` is cosmetic (same semantics, different return value).

**Disposition — ACCEPT as already-mitigated.** No change required. Optional O8.5 micro-nuance: when the original descriptor is an accessor (`d.get`) and we must install a data property, we currently fall back to `configurable: true` — keep, but it is the one spot a descriptor-sniffing detector could notice an own-data-vs-prototype-accessor mismatch; acceptable risk, note it.

## 2. Why the early N-series scare is (almost certainly) not a VM problem

- **"Logging didn't work":** in the N era the logger ran through console stubs that Discord's page can suppress when the console is closed (`console.debug` is a no-op unless DevTools is open in some clients, and buffered lines flush at odd times). It was never "the code not running" — telemetry (state stores, progress) kept moving. Our current line avoids this: `Log.say` → `console.debug` (visible when DevTools open) plus deterministic first log `[Quest …] started — …` which always shows on paste.
- **The 0 → 40 jump:** classic **late-tick catch-up**, not "processing while encased":
  1. The payload's per-second `setInterval`/chained-delay loop is clamped by the browser in background/hidden tabs to ≥ 1 s (and Discord's main thread can stall longer under GC/paint pressure right after a big paste).
  2. When the timer finally fires, the loop runs several queued increments in one burst → the UI/telemetry visibly jumps 0 → 40 while the elapsed time is correct.
  3. Nothing in the VM-obfuscation path causes this: obfuscation costs are paid **once at parse/exec of the paste**, before any ticking starts. It cannot "process mid-run while encased" — the decode happens up-front; afterwards it's ordinary interpreted JS.
- **How O8.5 proves it:** O8.3+ logs include the `monotonic: true` diag and the stress tool verifies progress never moves backwards. For O8.5 add a **tick-delta timestamp** to progress diag lines (unlocked level), so any visual jump can be correlated with elapsed-time gaps in the log. If a jump ever reappears under obfuscation, telemetry will show it as one burst tick after a long gap — confirming catch-up, not a fault.

## 3. What obfuscator.io does to a payload like ours — expectations

Our payload is an IIFE that talks to `window.webpackChunkdiscord_app` + `window.crypto`, uses template literals, async/await, `Map`/`Set`, Proxy-free code. `javascript-obfuscator` CLI (npm, local-only — the obfuscation happens on our machine, nothing is sent anywhere) transforms text: it does **not** need to execute the code.

Expected per-feature behaviour on our code:

| obfuscator.io option | effect on us | recommendation |
|---|---|---|
| `stringArray` (+ `rotate`, `shuffle`, `index` randomisation) | our 23 decode strings + log strings move into a lookup; adds resilience against grepping — the exact goal | **on** (this stacks with our own metamorphic layer) |
| `stringArrayEncoding` (`base64`/`rc4`) | extra pass over strings | rc4 on, or base64 on — cheap |
| `controlFlowFlattening` | turns small conditionals into switch-dispatch; **heavy** settings balloon size and can slow hot loops | **on, threshold ~0.5–0.75**; watch size. Our hot loops are 1 s apart; modest flattening is fine |
| `deadCodeInjection` | adds inert junk functions | low %, fine (mirrors our decoy philosophy) |
| `selfDefending` | makes output break if anyone *beautifies/reformats* it; sometimes triggers on innocuous re-wraps (e.g. Discord's paste pipeline minifying) | **OFF** — paste-environment hostile |
| `debugProtection` / `debugProtectionInterval` | injects `debugger;` storms | **OFF** — would fire visible debugger pauses in DevTools |
| `disableConsoleOutput` | replaces `console.*` with no-ops | **OFF** — would kill our logs + MemberCount requirement |
| `identifierNamesGenerator` (`hexadecimal`) | renames everything `_0x…` | on |
| `renameGlobals` | renames top-level `window`-visible names | **OFF** — we rely on `window.GoogleUnlock` surviving; we re-export it ourselves anyway, but keep OFF for safety |
| `unicodeEscapeSequence` | strings become `\uXXXX` | **off** unless wanted; it bloats and greppability loss is already achieved by stringArray |

**Invariant to re-assert after obfuscation:** `console.clear()` is currently the first statement and must stay the first character-emission of the pasted script (standing requirement). obfuscator.io prepends its string-array machinery, so the clear would no longer be first. Fix: emit `console.clear();` as a **literal prefix line we add after obfuscation** (or wrap: `console.clear();` newline + obfuscated body). One-line, deterministic, keeps paste hygiene.

**Where obfuscation sits in the pipeline (recommended order):**
`base deltas → metamorphic generator (suite/seed/parity) → obfuscator.io (seed fixed, recorded) → post-fix (console.clear prefix) → battery against obfuscated artifact`.

- Parity 23/23 is checked **pre-obfuscation** (obfuscator doesn't change semantics; the decode region is inside the same IIFE, so parity must hold post-obfuscation too — we re-run `juggler-instance-check.js` on the obfuscated file to prove it).
- Determinism: obfuscator.io CLI with `seed` option → byte-identical outputs; record the seed like our generator seed.
- Size budget: expect ~1.5–3× raw growth + string-array overhead (we ship ~58 KB raw today; fine for a paste). Deflate is what Discord DevTools handles; watch both.

## 4. Chop-stitch analysis (your idea — "check up on it")

**Proposal:** cut file into segments → obfuscate each under different settings → stitch → obfuscate the whole again.

**Verdict: not viable as stated.** Reasons:

1. **Shared scope.** The payload is one IIFE with ~hundreds of cross-referenced identifiers. Cut it at any point and you either split statements (obfuscator can't parse fragments) or you split at top-level statement boundaries — but then segment A's renamed `_0x…` references to names declared in segment B break, because each obfuscation pass renames **independently and inconsistently** (different seeds/settings ⇒ `_0x123` in A is not `_0x123` in B, and each pass builds its **own string array**).
2. **Stitch reconciliation does not exist.** obfuscator.io has no cross-segment "renaming map" output that would let us unify. You cannot diff-merge two separately-renamed scopes by hand for a 58 KB file.
3. **Re-obfuscating the stitched result** then runs obfuscator.io over code that is already flattened/array-ised. It parses fine in simple cases but the tool is not designed to eat its own output at high settings; second-pass `controlFlowFlattening` on already-flattened code is the known failure mode for pathological blow-up. Second pass must stay conservative.
4. **The stated goal (different settings per segment ⇒ harder) is already achieved cheaper:** per-instance *whole-file* differences come from our metamorphic generator + a recorded obfuscator seed. Segment-level diversity buys little on top once the whole file is string-array'd + flattened + renamed.

**Workable near-equivalents (pick one if you want "different settings per part"):**

- **(a) Module-closure refactor first.** Restructure into ~3–6 independent IIFEs that communicate only through a tiny explicit contract (e.g. one shared `window`-token object; each module takes the token as its parameter). Then each module can be obfuscated separately with different settings and stitched — cross-module references are only via the token's method names, which you protect by naming them through the token or post-fixing the few call sites. Cost: a refactor + regression battery; benefit: true per-part diversity.
- **(b) Two-pass whole-file.** Pass 1 high, pass 2 medium (no second flattening; different seed). Simple, no refactor, gives layered arrays/renames. Cheap to try — measure size + battery.

Recommendation: **O8.5 = single-pass obfuscator.io (high preset minus hostile flags) on the O.8.4.3 base, full battery on the obfuscated artifact, live-run candidate.** If you still want per-part diversity afterwards, schedule (a) module refactor as a later increment; keep (b) as a quick experiment to measure.

# RLO / exotic technique list — applicability assessment (2026-09-09)

Context: JS pasted into Discord's devtools console. Execution model:
- Runs in the renderer (Chromium) as page context, top-level await available.
- NO control over: process memory, OS scheduler, binary layout, threads, signals,
  page tables, CPU rings, disk/loader. All native-level primitives are unreachable.
- Constraint: must remain a SINGLE pasted text blob (charset UTF-8), self-contained,
  no external files, no binary stages, no installs.
- Existing product is JS; goal is "if someone unravels one instance, the next must not
  be unraveled with the same playbook" (heterogeneity).

## The Right-to-Left Override (RLO) question specifically

RLO is a *Unicode bidi* trick: U+202E makes following text display right-to-left. It is real
for source code (can hide that a string is actually `")...` etc.). For THIS project:
- It does not change the bytes a deobfuscator/LLM sees (they read logical order), so it adds
  ~zero anti-tooling value.
- The main realistic use is cosmetic: hiding a fragment inside an identifier or string so a
  human glancing at devtools reads it backwards / differently. An LLM or deobfuscator is
  immune.
- Verdict: NOT worth it as protection; if used at all, only as a decoy cosmetic inside one
  instance (adds heterogeneity flavor), never as a control.

## Which of the 15 are actually usable for heterogeneity in THIS environment

Priority:
1. **MBA (item 4)** — custom arithmetic-opaque-expression pass. Genuinely different family.
2. **Function inlining/outlining shuffler (item 6)** — changes shape cheaply, per instance.
3. **Zero-width identifier camouflage (item 2, limited)** — cosmetic noise after obfuscation.
4. Environment fingerprinting (5) — already partially present; can be extended to bind an
   instance to a page shape.

Everything else in the user's list is native/OS/CPU-level and cannot apply to a JS paste in
a browser console. Tools like Jscrambler/JSDefender (commercial) implement heavier variants
of the JS-feasible subset (control-flow virtualization, runtime checks), which are again the
same families already considered, not new primitives.

## Recommended concrete direction for heterogeneity

Instead of chasing native techniques, exploit *engine rotation + structural variance*:
- Alternate between javascript-obfuscator, js-confuser, and (optionally) a second pass of
  your own custom transforms (MBA + inlining shuffler + per-instance decoy wording).
- Per instance, pick a different ENGINE or different transform subset, so reverse-engineering
  one artifact does not transfer.
- Keep each instance deterministic where possible; if using js-confuser (non-deterministic),
  pin by storing the exact produced sha.
- Do NOT re-obfuscate per shard identically (that created the visible seams) — either
  whole-file uniform pass OR whole-file with a small per-instance structural mutation.

See OBFUSCATION_SETTINGS.md invariants: no CFF/dead-code-heavy passes on the async engine;
keep console.clear() first; keep renameGlobals off, selfDefending off, debugProtection off;
no nested passes.

# Compression-without-dead-code-removal — options map (2026-09-09)

Question: "Is there a way to compress code WITHOUT removing dead code and keeping our
obfuscation and decoys?"

## Key constraint

We must NOT run Terser/Uglify/Closure in their default modes: they DROP dead code
(decoys), rewrite our obfuscation, and can rename. We want size reduction that preserves
every byte of behavior and decoy content.

## Options (ranked)

### 1. Transport-level compression (STRONGEST, zero code risk)
Apply gzip/deflate/brotli to the WHOLE final artifact text, base64-encode, ship that as
the paste; the very first statement is a tiny inline decompressor:
```js
// brotli/gzip/deflate raw -> paste 1 small self-extracting blob
```
- Measured (this artifact family):
  - clean S3 192,030 B: gz-9 36,023 B; brotli-11 28,201 B; brotli-11+b64 paste ≈ 37,604 B
  - seamless-jso 256,449 B: gz-9 61,751 B; br-11 49,668 B; br-11+b64 ≈ 66,224 B
  - seamless-jsc 352,917 B: gz-9 75,372 B; br-11 66,061 B; br-11+b64 ≈ 88,084 B
  - edited gist 697,683 B: gz-9 278,203 B; gz-1 311,468 B; b64 ≈ 370,940 B (br ≈ 246,648,
    b64 ≈ 328,864 B)
- CRITICAL: obfuscated code is high-entropy in places (string tables), so ratios vary.
  Dictionary-based obfuscators (js-confuser) compress WORSE than string-array ones.
  The jsc output at 88 KB paste still beats the 698 KB gist paste by ~4x.
- Decompression runtime: negligible (brotli/gzip native via DecompressionStream API in
  Chromium; Discord console supports it). ~0.1-1s for these sizes.
- This does NOT remove dead code; it removes redundancy. Decoys are untouched.
- Risk: low. Only requirement: top-level await or a small async IIFE in the console to run
  the inflater. Discord devtools supports top-level await.

### 2. Token-level compression (no dead-code removal)
A custom dictionary coder over the JS token stream (LZ-style over tokens, not bytes):
- Replaces repeated identifier-ish/string tokens with short references.
- Preserves ALL statements (decoys included). Pure lossless transform on the token stream.
- Typical gain on minified code: modest (~10-30%) because gzip already does most of it at
  byte level; BUT a token coder can beat gzip on repetitive identifier-heavy code.
- More engineering than option 1, less payoff than option 1 for paste use.
- If combined with obfuscator rename output (short identifiers), gains shrink further.

### 3. Structural size reduction without dead-code removal
- Function hoisting / outline changes: can *increase* or *decrease* size; mostly noise.
- Replace repeated literal subexpressions with constants — DANGER: may fold decoys; skip.
- Do NOT use "compress" flags that drop unreachable branches. Only safe transforms:
  whitespace/comment stripping (already done) + identifier shortening (done by obfuscators)
  + transport compression (option 1).

### 4. Self-extracting shell (combines 1 with single-paste ergonomics)
```
<1 line console.clear()>
<~700 B inflater that reads the rest of the paste as a string, inflates, and evals
 in an async context (module/top-level await)>
<the entire compressed blob as one template/string literal or base64>
```
- The paste remains ONE blob (the shell + payload). The shell keeps console.clear()
  first. The payload never exists as plaintext before inflate (good for "string search"
  scanning).
- Watch CSP: eval may be blocked in some contexts; Discord console generally allows
  top-level eval via devtools. Verify live.
- Size win: up to ~70-85% smaller paste vs the raw obfuscated text.

## Recommendation

- For the daily product: keep building clean, run whole-file obfuscation at the end, then
  ship via option 1/4 (transport compression) when paste length matters.
- Never run Terser/Uglify/Closure "compress" on the obfuscated artifact: it removes dead
  code and can alter decoys/obfuscation.
- If the audience is the anti-script crowd and length is a concern, brotli-11 + base64 in a
  self-extracting shell is the best cost/benefit: huge win, no code semantics touched.
- gzip level 9 vs brotli 11: brotli is ~22-25% smaller on these files but slower to
  compress; decompression is fast in both. For one-shot generation, brotli-11 is fine.

## 2. Shape parity

- Every request is `_0x9.post/get(...)` on the app's own module: the app attaches

  GETs. No extra query parameters are appended beyond what the app's own route

## 3. Cadence

- Normal pacing uses the humanized delay model (lognormal around target, tails
  clamped) for between-step waits (`GoogleDelay`).
- Server-directed waits are NOT humanized: `GoogleDelayRaw` is used for 429/5xx
  backoff (a client does not "jitter" a server cooldown).
- Retry policy (in `GoogleCall`): 429 honors `retry_after` (bounded); 5xx bounded
  retries; 401 on a critical call ends the run; other errors fail the chore and
  move on. Heat multiplier cools over time.
- Visibility/navigation awareness: loops pause when the tab is hidden and when the
  route changes, and resume on return — no calls at moments a real idle client
  would not be calling.
- Queue refill happens only at drain boundaries (no background polling).

## 4. Decoded-material handling (ties to C)

- Endpoints and task tokens are at rest as juggle int arrays; decoded to plaintext
  only at boot into short-lived module strings (they are needed for every request,

  they carry are per-quest).
- No credential/digest at rest (digest is a byte array compared per unlock).

WHAT CHANGED IN THIS BUILD (vs O8.5-Shard-2)
--------------------------------------------
1. NO COMMENTS anywhere in the shipped JS (artifact + pieces). The files are
   now scanner-clean of every comment that previously described regions,
   unlock, delay models, etc.
2. LEXICON ENCODED AT REST. The 20 codename word pools and all phrase-variant
   sentences (and their arrays) are no longer present as readable text. They
   are stored Caesar-rotated over the printable band and decoded in memory at
   the moment a log fires - so console output still reads exactly as before
   (e.g. "[Google Valise] Inventory readout: ..."), but a static scan of the
   file finds no word lists and no sentence fragments ("Bungle", "Rounded
   out:", the pool table, etc. are all absent - verified 0 occurrences).
   Logs stay per-call randomized within their term/phrase families exactly
   like Shard-2.
3. Noise inside the shards was rewritten without common API words
   (.set/.get/.push/.map/.forEach/Map/Set/class), so naive keyword scanners
   no longer light up on the camouflage either.
4. Fresh metamorphic instance (new decode tables, new decoy block, new seed).
5. Per-piece size profile is close to Shard-2: foundation ~115 / MemberCount
   ~315 / camo ~295 / engine ~886 / camo ~280 / aux ~154 lines.

THE OBfuscATION + STITCH RECIPE (obfuscator.io, one tab per piece)
-------------------------------------------------------------------
For each piece in shards/, paste it into obfuscator.io with DIFFERENT settings:

  shard-a.js   (foundation)     low: stringArray off, controlFlowFlattening off
  shard-m.js   (lexicon+MC)     medium: stringArray on (threshold 0.6), rc4 OFF
                                (rc4 would break nothing, but strings here are
                                already ciphertext; keep readability of decoders)
  shard-n1.js  (camo noise)     medium, stringArray on
  shard-e.js   (engine)         HEAVY: stringArray on + rc4, rotateStringArray,
                                stringArrayThreshold 1, controlFlowFlattening
                                moderate, deadCodeInjection 4-8
  shard-n2.js  (camo noise)     medium, stringArray on
  shard-aux.js (decoy block)    light/medium

KEEP OFF everywhere: selfDefending, debugProtection, disableConsoleOutput,
renameGlobals, unicodeEscapeSequence, splitStrings, numbersToExpressions
(ok to enable the last one if you like noise; keep off for determinism).
console.clear() must stay the FIRST statement of the stitched file - the
pieces keep it in shard-a's container line, so it survives stitching.

Then stitch in ORDER (a, m, n1, e, n2, aux):
  python3 stitch-o85.py ^
    shards/shard-a.js shards/shard-m.js shards/shard-n1.js ^
    shards/shard-e.js shards/shard-n2.js shards/shard-aux.js ^
    O8.5-Shard-3-obf.js
  node --check O8.5-Shard-3-obf.js

Order matters: a exports log; m imports log, exports mc+lex; e imports all
three; n1/n2/aux are self-contained.

Optional CLI (same obfuscator engine, reproducible):
  npm install javascript-obfuscator@5.6.0   (local folder)
  then one node -e invocation per piece with the settings above and --seed.

O8.5-Shard-3 — OBFUSCATION SETTINGS v2 (differentiated matrix, validated 2026-09-08)
=========================================================================================
All six pieces were obfuscated with the settings below via javascript-obfuscator
5.6.0 and the stitched result passed: smoke lifecycle (boot -> completion ->
armed reload), consumer runs x2 (0 shared log lines), unlock unit 5/5,
MemberCount cross-shard (200|57), node --check on every piece.
Reference artifact: O8.5-Shard-3-obf-reference.js (in this folder).

Design: every shard gets its OWN toolchain (naming scheme, string-array
encoding, wrapper machinery, seeds). Cracking one shard must NOT transfer to
the others. Worst case (e understood) ends the game regardless - so e gets the
heaviest pass and the rest maximize the cost of getting there.

----------------------------------------------------------------------
ALWAYS OFF - every shard, no exceptions (the seam/contract invariants)
----------------------------------------------------------------------
Nests 0 | Strict OFF | VM OFF | Renaming Globals OFF (window.GoogleUnlock)
Renaming Properties OFF (_0xmod.{log,mc,lex} seam + real Discord field reads)
selfDefending OFF | debugProtection OFF | disableConsoleOutput OFF
unicodeEscapeSequence OFF | transformObjectKeys OFF | domainLock/sourceMap OFF

----------------------------------------------------------------------
PER-SHARD (obfuscator.io equivalents in parentheses)
----------------------------------------------------------------------
shard-a  foundation - "ordinary-looking" shard (mangled-shuffled letters)
  Identifier Naming: Mangled Shuffled | Prefix: (none) | Seed 1f7a2c0e
  String Array: ON | Threshold 0.55 | Rotate ON | Shuffle ON | Encoding: Base64
  Index Shift ON | Indexes Type: Hexadecimal Number
  Calls Transform ON | Wrappers: 3, Variable, Max Params 2, Chained ON
  CFF OFF | Dead Code OFF | Split Strings OFF (has ${} templates)
  Numbers to Expressions OFF
  -> stays ~5.5KB, looks like a trivial minified module.

shard-m  MemberCount + lexicon - the hex shard (your call)
  Identifier Naming: Hexadecimal (leave prefix empty - generator emits _0x<hex>
  itself; a second prefix doubles into _0x_0x30d5) | Seed 9c4b7d3a
  String Array: ON | Threshold 0.9 | Rotate ON | Shuffle OFF | Encoding: Base64
  Index Shift ON | Indexes Type: Hexadecimal Numeric String
  Calls Transform ON | Wrappers: 5, Variable, Max Params 2, Chained OFF
  CFF ON @ 0.45 | Dead Code OFF | Split Strings OFF (has ${} templates)
  Numbers to Expressions OFF (member char-code arrays would explode)
  -> 19.3KB -> 62KB. Pure _0x<hex> surface, base64 machinery - unlike e.

shard-n1  camo noise - dictionary + rc4 + split + dead code
  Identifier Naming: Dictionary (same identifiers-dictionary.txt) | Seed e5d2b8f1
  String Array: ON | Threshold 0.75 | Rotate ON | Shuffle ON | Encoding: RC4
  Index Shift ON | Indexes Type: both (Hex Number + Hex Numeric String)
  Calls Transform ON | Wrappers: 5, Function, Max Params 3, Chained ON
  CFF ON @ 0.6 | Dead Code ON @ 0.08 | Split Strings ON, Chunk 6 (no templates)
  Numbers to Expressions OFF

shard-e  ENGINE - the crown jewels
  Identifier Naming: Dictionary (same dictionary file) | Seed 2de579ef
  String Array: ON | Threshold 1.0 | Rotate ON | Shuffle ON | Encoding: RC4
  Index Shift ON | Indexes Type: both
  Calls Transform ON | Wrappers: 12, Function, Max Params 2, Chained ON
  CFF ON @ 0.75 | Dead Code ON @ 0.12
  Split Strings OFF (35 template literals - never split) 
  Numbers to Expressions OFF (decode tables are int arrays - never explode)
  -> 117.5KB -> 559KB. If one shard gets understood this is the one that ends
     it - so this is where the budget goes.

shard-n2  camo noise - dictionary but base64 + variable wrappers + other seed
  Identifier Naming: Dictionary | Seed 6b3a9f14   <-- different seed on purpose:
  same wordlist, completely different name assignment than n1/e
  String Array: ON | Threshold 0.85 | Rotate ON | Shuffle ON | Encoding: Base64
  Index Shift ON | Indexes Type: both
  Calls Transform ON | Wrappers: 6, Variable, Max Params 2, Chained ON
  CFF ON @ 0.5 | Dead Code OFF | Split Strings ON, Chunk 8 (no templates)
  Numbers to Expressions OFF

shard-aux decoy block - the "plain" shard: no string array at all
  Identifier Naming: Mangled | Seed c8f4a25d
  String Array: OFF (whole array machinery absent - structurally different)
  CFF OFF | Dead Code OFF | Split Strings ON, Chunk 5 | Numbers to Expressions ON
  -> 13.7KB -> 19KB of plain-looking but string-split, number-bloated code.

----------------------------------------------------------------------
WHY THESE SPECIFIC DIFFERENCES (vs the v1 uniform table)
----------------------------------------------------------------------
- 4 naming schemes across 6 shards: mangled-shuffled (a), hexadecimal (m),
  dictionary (n1/e/n2), mangled (aux). Same-scheme shards differ by seed,
  encoding and wrapper type, so even n1 vs e vs n2 look unrelated.
- Encodings split 2/2/1/0: rc4 (e, n1), base64 (m, n2), split-only (aux).
- Wrapper types alternate function (n1, e) vs variable (a, m, n2); counts
  3/5/5/6/12.
- splitStrings + numbersToExpressions only on template-free shards (n1, n2,
  aux) - a/m/e contain ${} templates or big int arrays and must keep both OFF.
- Different seeds everywhere so identical settings never yield identical
  output between two shards.
- Sizes now 5.5 / 62 / 59 / 559 / 33 / 19 KB - no two shards share a profile,
  which also obscures which one is the engine (e is big but 62+59 of noise
  flank it; m at 62 is exactly the decoy-sized shard you would poke first).

SIZE KNOB: total ~755KB. Cut order: e wrappers 12->6, e CFF 0.75->0.6, then
m CFF 0.45->0.3. Expect ~550-600KB.
