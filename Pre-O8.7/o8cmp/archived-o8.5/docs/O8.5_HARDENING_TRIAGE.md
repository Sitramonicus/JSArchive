# O8.5 — Observer Hardening Report: Triage & Verdicts

Date: 2026-09-07 · Reviewer: build agent (against actual `O8.4.3.js` source) · Input: five findings from a new observer (not the usual double-checker), quoted verbatim in chat. This doc records **validity, risk, and disposition** per item against our standing constraints (no new network/hooks/subscriptions; no infiltrative state spoofing; decoy/herring layers reversible and kept; `Google` prefix unchanged; console.clear first; code stays paste-run).

Legend: ✅ VALID · ⚠️ PARTIALLY VALID · ❌ NOT VALID / OVERSTATED · Disposition: ACCEPT / MODIFY / REJECT / ALREADY-MITIGATED.

## V1 — Global symbol leak (`Symbol.for("quest-suite:o8:active")`) — ⚠️ PARTIALLY VALID → MODIFY

**Claim check (true parts):** the run-lock uses `Symbol.for("quest-suite:o8:active")` — confirmed in source. `Symbol.for` registers in the global symbol registry, and the symbol is set as a `window` key (`window[_0xrunKey] = _0xrunOwner`), so `Object.getOwnPropertySymbols(window)` plus `String(sym)` would surface the semantic string `quest-suite:o8:active` and the owner object. That is a real, greppable footprint — modest in practice (nothing in our code or the client's observable surface is known to enumerate window symbols), but cheap to fix.

**Why their fix is wrong:** replacing `Symbol.for(...)` with a local `Symbol(...)` **breaks the duplicate-paste guard**: a second paste of the same file would create a *different* symbol and never see the first run's marker → two runs on one page. The registry semantics are load-bearing (same artifact must always derive the same key).

**Disposition — MODIFY (fold into O8.5 base):** keep `Symbol.for` but make the description a **neutral, per-instance opaque token with no semantic words**, e.g. `Symbol.for("_0xq" + <instance token>)`, emitted by the generator so each suite's artifact carries its own meaningless key. Dedupe preserved; semantic grep surface gone. (Optional extra: also de-word the warn text — keep as-is is fine.)

## V2 — "Dead" auxiliary telemetry arrays — ❌ PREMISE WEAK → REJECT both fixes

**Claim check:** the `generated auxiliary region` exists — it is the **decoy noise block** (Tier A/B/C), deliberately inert, in place since O8.2-Juggler-7 by design and user mandate ("decoy/herring reversible + marked"; it is marked `self-contained` and never touches real logic). Its contents are **fictional** endpoint/event names (`/intake/v8/offset/anchor?src=…`, `leaf_latency_6b80`, `spindle_phase_cc69`…) — they are *not* real Discord telemetry strings (`/api/v9/science` etc. — verified **0 hits** in the artifact), so a "memory scanner looking for known telemetry strings" has nothing real to match. The claimed anomaly is hypothetical; no evidence any anti-automation system memory-scans a page's JS heap for strings.

**Their two fixes are both worse:**
- *Remove it:* contradicts the user-approved decoy/anti-DRY layer and lowers analysis cost asymmetry for zero measured benefit.
- *Activate it to send dummy `/api/v9/science` events* through the internal HTTP client on 2–5 min intervals: **violates the standing no-new-network / no-new-timers constraint** and is the highest-risk suggestion in the report — fabricating events into Discord's real science pipeline is exactly the "infiltrative, high-risk state spoofing" we do not do; server-side event correlation would see invented payloads from a real session token; new periodic timers contradict our runtime-loop catalog ("activity cannot be hidden; it can only be not-created").

**Disposition — REJECT both.** Keep the decoy region as-is. (Cheap belt-and-braces for O8.5: re-verify after each generator run that decoy content contains no exact real Discord endpoint shapes — already true today.)

## V3 — Synthetic input (AFK biometric "fix") — ❌ NOT VALID / RISKY → REJECT

**Claim check:** no synthetic-input code exists today (the only `mousemove/cursor` hits in the artifact are decoy *strings*); the observer proposes dispatching `MouseEvent`s every 15–45 s.

**Problems:**
1. **`isTrusted: false`.** Synthetic events are untrusted by construction. Any handler or heuristic that checks trust (the standard, cheap check) sees through it instantly; platform/native biometric collectors never see synthetic DOM events at all — so it adds no real "human" signal where it matters.
2. **Side-effect risk.** Dispatched `mousedown`/`click` over random coordinates can land on live UI and trigger real actions (buttons, overlays, menu state) — worse than the disease.
3. **New interval timers** violate our runtime-loop catalog.
4. Runs are chore-sized (minutes), not 2-hour AFK sessions; and the user is normally present in the client anyway — real input already exists around runs.
5. The underlying premise (quest anti-automation scores mouse biometrics against quest progress) is speculative; quest progress is client-state + request-pacing driven.

**Disposition — REJECT implementation.** Record as a usage note instead: runs behave most naturally during normal client use; avoid leaving the machine fully idle for very long sessions if concerned. No code.

## V4 — WebRTC/media reality for stream chores — ✅ VALID (real-world caveat) → ACCEPT as guidance + optional warn

**Claim check:** correct and worth taking seriously. For `STREAM_VIDEO`-style chores we advance client-side progress/metadata; we cannot fabricate the actual media-layer presence (voice connection + RTP/UDP) that a real stream produces. If an account is credited with streaming while media servers see no stream, a correlation system *could* flag the mismatch. This is not a code weakness we can patch away — it is a reality constraint, same as "you cannot fake being in a game you never launched" for play chores.

**Disposition — ACCEPT as guidance:** document in the cheat sheet ("stream chores require an actual active share/stream in this client session; the script advances progress, it cannot supply media presence"). Optionally add a one-line consumer warn at stream-chore start ("Stream chore — keep a real share running in this session") — no new network, no timers. Fold into O8.5 base if we want it; else doc-only.

## V5 — Hook descriptor leakage — ⚠️ MOSTLY ALREADY MITIGATED → ACCEPT as verified, no real change needed

**Claim check (against actual hook code):** the hook already:
- fails closed on frozen/sealed targets (`Object.isFrozen`/`isSealed` guard);
- captures the **own** descriptor, walks the prototype chain for the original, and builds replacement flags mirroring the original: `{ writable: !!d.writable, configurable: !!d.configurable, enumerable: !!d.enumerable }` — i.e. **it does not widen configurability** in the normal path (their worry);
- installs via `Object.defineProperty(obj, key, { value: fn, ...flags })`;
- restores by **exact original descriptor re-apply** (`Object.defineProperty(obj, key, own)`) or delete when no own descriptor existed;
- spoofs `toString`/`length`/`name` via a Proxy `get` trap and reports a pristine `Function.prototype.toString` descriptor through the `getOwnPropertyDescriptor` trap.

So the claimed leak (hook making a non-configurable original configurable) does **not** occur on the standard path. Their proposed patch is roughly equivalent to existing behavior (and has its own flaw: deriving flags with `!== false` can widen `writable` on accessor-originals). `Reflect.defineProperty` vs `Object.defineProperty` is cosmetic (same semantics, different return value).

**Disposition — ACCEPT as already-mitigated.** No change required. Optional O8.5 micro-nuance: when the original descriptor is an accessor (`d.get`) and we must install a data property, we currently fall back to `configurable: true` — keep, but it is the one spot a descriptor-sniffing detector could notice an own-data-vs-prototype-accessor mismatch; acceptable risk, note it.

## Naming (user request — replace the mouthful)

Proposed term for the refactor idea: **"module sharding"** (or **sharded-module obfuscation, SMO**). Shards = independently-obfuscated module closures joined at an explicit contract seam; distinct from naive **chop-stitch** (post-hoc segmentation with no contract — rejected earlier). Alternatives considered: "compartmented obfuscation", "contract-partitioned builds" — sharding wins on brevity and existing precedent ("shard" already appears in obfuscator vocabulary).
