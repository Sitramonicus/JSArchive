# O8.2-Juggler-4 — decoder logic + coverage logging (2026-09-06)

sha256 `9ed27d5a91b09336abfc08fcafabf5594081c41b1e11b43a3195440807199222`

## 1. Which mode made your O8.2-Juggler-3 live run "work"?

**The embedded (polymorphic) key fallback — not environment-derived keys.**

In J-3 (and J-4 as shipped) every constant is `_0xJuggle([0], [42, ...])`. The first guard in
the decoder is:

```js
if (!ep || ep.length <= 1 || ep[0] === 0) { /* embedded fallback only */ }
```

`ep = [0]` means **the env matrix is not armed** — it is compiled into the payload but never
executes. All 23 strings decode via `fp[0] = 42`. That is why it worked identically to plain
O8.2: same ciphertexts, same key, same result. It is deterministic, not "env-derived that
happened to agree".

J-4 now *proves* this on every run: the coverage line prints
`embeddedFallbackOnly: 23, envMatrixArmed: 0, envDecoded: 0`.

## 2. Decoder logic (as originally conceived vs. as built)

### Original idea (J-1 / O7.42 era)
- Ship each string encrypted under a key derived from the client environment: 5 sources × 4
  hashes = 20 combos. At runtime, try each combo; first decode passing a printable-sanity
  regex wins; if all fail → embedded fallback key.

### Why that design is dangerous (confirmed by testing)
1. The sanity regex is weak: XOR garbage over letter-ish ciphertext can itself be letter-shaped
   and pass. First-valid-wins can therefore return **garbage as an "env hit"** (my unit test
   reproduced this: a wrong key produced a valid-looking but wrong string).
2. If env arrays are mis-built (the O7.42 corruption class: 2–3/22 strings decodable under any
   key), the old decoder returned silent garbage or logged per-constant fallback spam —
   exactly the "tons of errors piling up" you saw.
3. Any real env mode must coexist with a fallback (canary), so an analyst can always force the
   fallback — that exposure is inherent to the dual-mode design, not a bug.

### O8.2-Juggler-4 decoder (cross-check design)
- **Mode B (shipped): `ep = [0]`** → embedded fallback only. Deterministic, zero env risk.
- **Mode A (armed, via builder): `ep = [key, ...bytes]`** → evaluate the full 20-combo matrix,
  but **credit env only when a combo's decode exactly equals the embedded fallback decode**
  (key agreement). A random garbage decode can never match, so env mode cannot return garbage;
  if the client changes and env keys stop agreeing, every string logs `env-miss` and falls back
  — the canary you originally wanted, without the crash cascade.
- **Fallback sanity check:** every embedded/fallback result is regex-checked. A corrupt array
  (O7.42 class) now raises one clear `[Juggler] … corrupted array?` warning instead of silently
  poisoning the run with `wepackChunkdiscord_app`-style strings.

## 3. What the new LOG_LEVEL = 2 logs look like

Per constant (23 lines):
```
[O7-DIAG] Juggler decode {name: '_0xq0', mode: 'embedded-fallback', key: 42, len: 23, valid: true}
[O7-DIAG] Juggler decode {name: '_0xq1', mode: 'env', source: 'DiscordNative.app.getVersion', hash: 'djb2-ish', key: 214, combosConsistent: 3, len: 13, valid: true}
[O7-DIAG] Juggler decode {name: '_0xm0', mode: 'env-miss->embedded-fallback', key: 42, envSourcesAvailable: 5, combosConsistent: 0, len: 34, valid: true}
```

One aggregate (after the 23rd constant):
```
[O7-DIAG] Juggler coverage {
  total: 23,
  embeddedFallbackOnly: 23,      // or 0 when armed
  envMatrixArmed: 0,             // >0 when ep arrays are armed
  envDecoded: 0,                 // >0 when env keys agree with embedded plaintexts
  envMissThenFallback: 0,        // >0 when armed but env keys no longer agree (client update)
  fallbackSanityWarnings: 0,     // >0 = corrupted array detected
  envSourcesUsed: 'none (env path not exercised)',  // e.g. {DiscordNative.app.getVersion: 23}
  envHashesUsed: 'none …',                            // e.g. {djb2-ish: 23}
  embeddedKeys: ['_0xq0', …],    // which constants used the embedded path
  envKeys: 'none'                // which constants used the env path
}
```

Interpretation guide:
- `envMatrixArmed: 0` → you are running the deterministic line (nothing env-derived happens).
- `envDecoded: 23, envMissThenFallback: 0` → genuine env coverage; env keys reproduce every
  constant. This is the "it really is environment-derived today" state.
- `envDecoded: 5, envMissThenFallback: 18` → partial agreement (e.g. some sources empty or a
  hash no longer matches); still safe, still works, but env coverage is partial.
- `envDecoded: 0, envMissThenFallback: 23` → client changed; every string fell back cleanly.
  No errors, no cascade — the canary did its job.
- `fallbackSanityWarnings: N` → stop: arrays are corrupt (rebuild with the builder).

## What changed (the five layers, this instance)

The env-matrix concept is **deleted** (user decision). In its place, an offline generator re-encoded the 23 plaintexts (manifest `juggler-strings.json`) into a structurally unique payload:

1. **Per-string keys** — every array carries its own key/params; no global key exists. (The old single 0x2A/42 is gone entirely.)
2. **Per-string mechanisms** — 4 mechanisms, assigned per string: xor, add, rotate-then-xor, 256-entry shuffled table. This instance: method order in code is rot=idx0, tbl=idx1, xor=idx2, add=idx3; usage rot 4 / tbl 8 / xor 8 / add 3.
3. **Instance alphabet** — one 256-byte permutation `_0xT` (reshuffled per instance) used by the table mechanism; inverse `_0xTi` built once at boot.
4. **Pool blob** — 13 of 23 strings merged into one 249-byte blob `_0xPool`; their call sites are (offset,length) slices: e.g. `_0xq0 = _0xJuggle([1,-16,85,23], "_0xq0")`. Kills the "23 tidy arrays" pattern.
5. **Generator randomness** — everything above re-rolled per seed; the fIdx→mechanism meaning, keys, table, blob layout all differ between instances.

Decode format: `[fIdx, …params|mark,off,len…, …bytes]`; marker value `-16` in this instance (negative ⇒ pool slice; params are always ≥1 so no ambiguity). Coverage logging retained, env fields removed.

## What the Lazy Forcer is for
Discord's webpack runtime keeps two tables on the module function: `_0x2.c` = **instantiated**
modules (factories already executed), `_0x2.m` = **definitions** (factories not yet run; the client
instantiates lazily). Pocket discovery only scans the instantiated cache. In the O7.34-era client the
cache was tiny (~102 entries) vs ~8.4k definitions, so required stores sometimes simply were not
instantiated yet → pockets missing. The forcer walks `_0x2.m`, finds definitions whose **source text**
contains one of the decoded target method names, and executes that factory `_0x2(id)` so the module
lands in `_0x2.c` and the scan can find it.

History: O7.35 tried this (forced 232 → cache 2,112) and pockets still weren't found — the real fix

# O8.2 live 404 — root cause confirmed (2026-09-06)

## What the live runs show

Both the **O8.2-Juggle (broken parent)** run *and* the **O8.2-Juggle-fix** run produce the
same 404, at the same point, with the same stack:

```
[Google Mailroom] Memo slipped under the door — shift started.
[O7-DIAG] Delay sample {count: 1, milliseconds: 6069, heat: 1}
GET https://discord.com/[object%20Object] 404 (Not Found)
   (anonymous) @ 556707…js:455      ← Discord's OWN fetch wrapper (file, not VM)
   apply @ 556707…js:468
   (anonymous) @ 620620….js:12      ← Discord internal (loading chunk 12)
   setTimeout
   sleep @ VM:412 → GoogleDelay @ VM:444 → _0xboot @ VM:741
```

Critically, the same 404 appears in the **O8.2 stable run's own log** (the one labeled
"working", first gist `fc9a…`, lines ~774–810) — at the identical boot point, with the
identical `Discord internal chunk 12` stack — and *that run still completes the quest* and
reaches "Shelf polished … (1 activity result)".

## Interpretation: the 404 is NOT from the quest script's own requests

Evidence:
1. The failing frame is `556707…js:455` → `apply @ …js:468` — **Discord's own network
   layer**, and the caller chain `620620….js:12` (repeated) is **Discord's module loader**
   — NOT the VM (the pasted script has no file/line numbers; its frames are `VM58765`).
2. It happens *during the first `GoogleDelay` inside `_0xboot`*, **before any
   `GooglePostSafe`/`GoogleGetSafe` runs**. There are zero `[O7-DIAG] HTTP url` lines and
   zero `[O7-DIAG] URL id …` lines — my transport guard never saw the URL because the
   request never went through my wrappers.
3. The script's own request sites are all guarded; the only raw network access is
   `_0x9.post/_0x9.get` bound through `GoogleCall`. No unguarded `fetch`/`xhr` exists.
4. The URL `https://discord.com/[object%20Object]` — i.e. an object stringified into a
   bare path with no route prefix — is not a shape any `GoogleRoutes` builder produces
   (they all start `/quests/…`, `/applications/…`, `/heartbeat`). So the object is being
   concatenated by *Discord-internal* code into a *relative* URL.

## The actual trigger (mechanism)

`window[DiscordNative].app.getVersion()` is probed during discovery and the **deep scanner
iterates and instantiates lazy webpack modules** (the "Lazy Force": 50 executions, cache
8263→8398). Instantiating arbitrary Discord modules as a side effect can make Discord's own
module loader fire internal requests. One of those internal requests gets built with an
object (a Discord-internal bug/pattern under this client build) → the loader asks its fetch
layer for `/[object Object]` → 404 → the error (an HTML page) is what surfaces in the log.

So: **the 404 is a side effect of the lazy-module forcer/deep-scanner, not of the
URL-id code.** This is consistent with:
- O7.34–O7.35 findings: forcing lazy modules can change client state and fire side effects.
- The "working" O8.2 stable log: it also forces modules (Lazy Force 50, cache delta 135),
  gets the same 404, yet its *quest-runner* still completes — because the 404 is an
  internal request failing in the background, and the script's own guarded quest calls are
  unaffected.

## Why my fix didn't remove it

I fixed the *quest-runner's* URL/id handling (videoProgress/applications/heartbeat →
GoogleId + transport guard), which is correct and necessary for the quest requests. But the
404 originates from the **forer's side-effect instantiation** path, which my single-subsystem
revision intentionally did not touch. Hence: same 404, same boot placement, zero URL-id diag.

## What "working O8.2" really means

O8.2 stable "works" in the sense that the *quest completes* despite the background 404.
The visible "error" in the console is Discord-internal noise from the forcing side effect —
it does not abort the quest. So the correct acceptance criterion is not "no 404 in console",
but "quest completes; guarded requests succeed". The Juggler-fix achieves that (quest
completed in the fix run too).

## Recommendations (options)

A. If the goal is a **clean console** (no Discord-internal 404): the fix is to stop forcing
   lazy modules — remove/limit the Lazy Force (or make it non-instantiating: only scan
   `_0x2.m` source text without calling `_0x2(id)`). This matches the O7.35 conclusion:
   "executing definitions was not the repair" and "must not be included in the maintained
   line". That is a single-subsystem change (forcer only), separate from URL handling.

B. If the goal is quest completion: it already works; the 404 is benign background noise.

C. To confirm: run once more with the forcer **disabled** and `LOG_LEVEL = 2`. If the 404
   disappears, the forcer side-effect theory is confirmed. If it persists, capture the
   console *before* the run and compare — Discord itself may fire such a request on load.

const _0xln = (ms) => {
  const u1 = Math.random() || 1e-9, u2 = Math.random() || 1e-9;
  const z = Math.sqrt(-2.0 * Math.log(u1)) * Math.cos(2.0 * Math.PI * u2); // Box-Muller

// Server-compliance wait: raw, un-jittered (429 retry_after / 5xx backoff).
const GoogleDelayRaw = async (ms) => {

    try { await sleep(chunk, signal); } catch (e) { if (e.name === 'AbortError') return; throw e; }

};

## Changes

**Channel B (behavioral):**
1. **Humanized delay model — log-normal split.** `GoogleDelay(d)` now uses Box-Muller log-normal (`_0xln`, σ=0.35) around the target in *seconds*: median = target exactly, mean ≈ +6%, tails clamped [0.3×, 4×] (verified 50k-sample stats). Hidden-tab penalty (+2–6 s), 12% burst (+1.8–4 s), and heat multiplier unchanged. Config diag: `delayModel: "lognormal"`.
2. **Server-compliance waits separated (`GoogleDelayRaw`).** The 429 retry-after and 5xx backoff paths call raw ms waits — never humanized (a blanket conversion would violate retry-after and cause 429 loops). Unit-verified paths in `GoogleCall`.
3. **Macro rest cycles.** New session budget 35–50 min (randomized per run); when exceeded and work remains, one 12–20 min rest happens **between chores** only (`Siesta` log, `GoogleDelayRaw`), never mid-task, never after idle, abort-aware; window resets after rest. Does not fire in any harness run (budget ≫ test length).

**Channel A (static):**
4. **Output-only per-instance identifier rotation.** 8 neutral helper identifiers (`recordDelay`, `sanitizePath`, `extractHttpProgress`, `findTaskConfig`, `registerCleanup`, `activeTasks`, `sleep`, `maybeRest`) are renamed to fresh hex names per instance by the generator (word-boundary replace, validated 0 residual tokens). 5. **Regex-noise.** The decode sanity regex is built at runtime from a char-code array (`_0xJRe`) — no plaintext pattern literal in the file.
