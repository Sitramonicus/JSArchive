# String-layer reversal — bundle 2 deliverable

**2026-09-18.** Read-only investigation; no build files were modified. This is the prerequisite for
R2-01 and R2-03.

**Confidence key:** everything below marked **[source]** was read directly out of the build scripts
and is certain. Items marked **[not demonstrated]** are reasoning I have *not* proven with a
working extraction — a Python brute force timed out at 10 min and the real sweep needs C, which is
how the red-team did it.

---

## 1. The layer, end to end

**[source]** `Active/O8.13/oto/scripts/obf-strings-g7.js`.

```js
// :48  build-time keystream twin of the shipped dec() (xorshift32 over char index)
function ksByte(skey, pos, i) {
  let st = (skey ^ Math.imul((pos + 1) >>> 0, 2654435761)) >>> 0;
  for (let k = 0; k <= i; k++) { st ^= (st << 13) >>> 0; st ^= st >>> 17; st ^= (st << 5) >>> 0; }
  return st & 255;
}
// :53
function encEntry(s, skey, pos) {
  const bytes = [];
  for (let i = 0; i < s.length; i++) {
    const c = s.charCodeAt(i);
    bytes.push((c & 255)          ^ ksByte(skey, pos, bytes.length));
    bytes.push(((c >>> 8) & 255)  ^ ksByte(skey, pos, bytes.length));
  }
  return Buffer.from(bytes).toString('base64');
}
```

So: every string literal of length ≥ `MINLEN = 4` becomes UTF-16LE bytes, XORed against an
xorshift32 keystream, then base64. Decode is the mirror image.

### The three facts that decide the whole design

**[source] 1 — The key is 32 bits.**

```js
// :162
const skey = Math.floor(rnd() * 0xffffffff) >>> 0;
```

One key per tag, drawn from `mulberry(seed)` where `seed` comes from `SEEDINT` (`seed-lib.js`).
The full key space is **2³²**.

**[source] 2 — `pos` is not a secret.** It is the entry's index in the shuffled table
(`:181 table = order.map((o, pos) => encEntry(..., skey, pos))`), i.e. a small integer. And
`ksByte` mixes it as `skey ^ Math.imul(pos+1, 2654435761)` — a **multiply by an odd constant,
which is invertible mod 2³²**. So `pos` adds no key material whatsoever.

**[source] 3 — the known plaintext is sitting in the build script, unencoded.**

```js
// :72  TUBE_TPL
'reel layer {n} ok ({p}% mapped)',  'chunk {n} sealed, key {h}',
'gate {n} open -- subkey {h}',      'chain {n}: {p}% converged',
'lattice L{n} settled ({p}%)',      'schedule K{n}: {h}',
'shroud {n} lifted ({p}%)',         'wheel W{n} aligned: {h}',
```

These are exactly the eight strings the red-team report lists as recovered. They are plaintext in
`obf-strings-g7.js`, and `TUBE_SKELETONS` (`:82`) is derived from them by replacing `{n|p|h}` with
`\0`.

### Put together

**[reasoning, not demonstrated]** A 32-bit key plus abundant known plaintext means a
known-plaintext attack recovers `skey` for each tag. The red-team's own brute force was 2³² in C
at ~2m40s per blob (`rF2kkpYJO.md` NODE 738-739) and scored 18/32 because they were guessing the
*plaintext shape*, not using the templates. **Handed the templates, the attack is strictly easier.**
I did not run a successful extraction myself — the Python attempt timed out — so treat the
difficulty as "the red-team already did it", not as "I proved it".

## 2. Where the "51 alphabets" come from

**[source]** `obf-strings-g7.js:65`:

```
// r3 K: 104->12 alphs runtime permute (only 12 b64 TBLs ship, rest via FY perm of alphabet using SKEY)
```

Twelve base64 tables ship; the remainder are generated at runtime by a **Fisher-Yates permutation of
the alphabet keyed by `SKEY`**. That is why the report could recover "51 unique 91-char alphabets"
while no alphabet literal exists in `shards/*.js`.

**Consequence:** the alphabets are a *function of the same 32-bit key*. Recovering `skey` yields
every alphabet. The 51-alphabet design adds no independent security — it is one secret wearing 51
hats.

## 3. Correction to my earlier claim

I previously wrote that the 13,346-char / 91-distinct blob in `stego11p-real.min.js` was "a base91
alphabet repeated ~146×". **Wrong.** Measured this bundle:

- `shard-m.js`'s `_0xpb` literal is **2,509 chars, 54 distinct** — a *different, smaller* object,
  decoded by `_0xwd` (`shard-m.js:6`) via a 2-char length prefix and a fixed `+47 mod 95` offset.
- The shipped **13,346-char / 91-distinct** blob appears in **no shard** (searched all
  `shards/*.js` and `oto/scripts/*.js` for literals 12,000–15,000 chars; only hit was an unrelated
  14,944-char string in `shard-e.js`). It is **generated by the pipeline**, consistent with §2.

So the blob is generated alphabet material, not a repeated alphabet, and `_0xwd`/`_0xpb` are a
separate small mechanism from the main string layer.

## 4. What this means for the fixes

### R2-01 was aimed at the wrong thing

The plan said "replace the fixed alphabets with per-call-site PRNG-derived alphabets". But the
alphabets are *already* key-derived — that is not the weakness. **The weakness is a 32-bit key with
known plaintext in the same repository.** Per-call-site alphabets would not change that at all.

**R2-01 restated: widen the key and remove the known plaintext.**

- **R2-01a — widen the key.** 32 bits → at least 128. `ksByte`'s xorshift32 state would need to
  become a wider PRNG (xorshift128 or a counter-mode stream from SHA-256). Cost: a few lines in
  both the build-time twin and the shipped `dec()`, which must stay in lockstep. This alone takes
  brute force from "2m40s in C" to "not happening".
- **R2-01b — get the templates out of the build script.** `TUBE_TPL` and `TUBE_SKELETONS` are the
  KPA oracle. Generate them procedurally at build time from a non-literal source, or stop emitting
  structured English. **Note this is a source-hygiene issue too**: the operator intends to push the
  workspace to GitHub under `@~8.13`, which would publish the oracle alongside the payload.

### R2-03 (shatter the string table) is still valid but secondary

The 303,327-char contiguous array is liftable in one read. Splitting it and interleaving decoys
raises the cost of *locating* entries — but once `skey` is known, location stops mattering. Do it
after R2-01a, not instead of it.

### A stronger option worth pricing: bind the key to runtime

The deepest fix is to make static extraction impossible rather than slow: derive the string key from
something only available at runtime, so the table cannot be decoded without executing. That is a
real architecture change (the strings are needed early, before the environment is verified) and it
interacts with R2-05 (unforceable gates). Worth a decision before r2 build starts, because it
changes where the key comes from everywhere else.

## 5. Suggested bundle 3

**R2-01a + R2-01b together**, since they are the same edit site and the same verification:

1. Widen `ksByte`/`encEntry` and the shipped `dec()` to a 128-bit key in lockstep.
2. Remove `TUBE_TPL` / `TUBE_SKELETONS` literals; generate procedurally.
3. Rebuild the cascade, then **verify by attempting the attack** — a C sweep for the old 32-bit key
   must fail, and the shipped `dec()` must still round-trip every string.
4. Full gate set (battery 25/25, tiers 43/0, gated 10/10, 16-point).

The round-trip check in step 3 is the one that matters: the build-time twin and the shipped decoder
have to agree exactly, and that is the failure mode most likely to produce a silently dead payload
— the same class of failure as the R2-02 attempt.
