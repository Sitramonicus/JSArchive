# O8.13-r3 live-test incident record

**Reported:** 2026-09-19 (exact live-test timestamp not supplied)  
**Release under test:** O8.13-r3  
**Status:** combined CC-02+03 candidate simulated PASS; real-host/live gate HOLD; O8.13-r3 remains frozen; no release bytes changed  
**Evidence:** user-supplied console log at <https://ctxt.io/3/pqCPI3AQg.md>

## Executive classification

The log does **not** establish a native Discord process crash. It does establish a renderer/application failure state with uncaught asynchronous exceptions, substantial main-thread stalls, host-side activity/overlay churn, and a console-history storage-quota failure. The generic “Discord has crashed unexpectedly” screen is therefore treated as a serious live-test incident even though the available evidence does not include an OS crash dump.

Live testing is paused. Do not run O8.13-r3 or the combined candidate against a real account until a bounded real-host diagnostic review is complete. Do not promote the candidate.

## Observed evidence

- The script booted, found the expected local board state, started work, and emitted normal-looking progress/completion messages.
- Discord then reported an uncaught promise error in its own loaded module graph: an undefined value was accessed while reading `GAME_SERVER_SUBSCRIPTION_CHECKOUT`.
- The log later recorded another uncaught Discord-side UI/navigation error while transitioning to a channel: an undefined value was accessed while reading `$`.
- Discord logged `RunningGameStore` changes, overlay tracking/untracking, overlay-method updates, and repeated performance-snapshot failures while synthetic activity records were present.
- The log contains repeated long-task warnings: message, timer, interval, focus/blur, animation-frame, and forced-reflow handlers reached materially high durations.
- DevTools attempted to persist a roughly tens-of-megabytes console history and failed its storage quota. The initial `console.clear()` did not prevent that persisted-history failure.
- An audio-input warning involving the user’s OBS/Voicemeeter devices appears independent of the script failure and is not treated as the primary cause.
- Discord’s normal network activity and RTC heartbeats continued after the first exception, so the first error was not an immediate total process termination.

## Likely contributors, ranked

### 1. Console/log accumulation — high confidence contributor

The persisted console-history quota failure is direct evidence of unbounded diagnostic output. Repeated progress, heartbeat, overlay, and application logs can exhaust DevTools storage and increase renderer memory/latency. This is sufficient to make the session unstable even if it is not the original exception.

### 2. Synthetic running-game updates — high confidence risk surface

The O8.13 source path inspected for this incident temporarily replaces running-game accessors and dispatches running-game change events while a task is active. The live log shows Discord’s own RunningGameStore and OverlayBridge reacting to those records. That creates host work outside the intended task loop: overlay decisions, performance snapshots, IPC/RPC activity, and additional event handling.

The repeated “performance snapshot not available” messages and overlay churn show that the host is treating at least some synthetic records as real enough to process. This is the strongest candidate for the high-latency cascade and for triggering unrelated Discord code paths.

### 3. Discord-side module/API mismatch — medium confidence

The `GAME_SERVER_SUBSCRIPTION_CHECKOUT` exception occurs inside Discord’s current loaded chunks, not inside the pasted file’s visible stack. It may be an independent Discord rollout defect, or it may be a host path reached because of the synthetic activity/overlay events. The log alone cannot distinguish those cases.

### 4. Navigation/UI state fault — medium confidence

The later `$` exception occurs during channel navigation and React error handling. It may be fallout from the earlier renderer pressure or a separate Discord UI defect. It should not be attributed to O8.13-r3 without a clean control run.

## Cause determination — follow-up

The source/log correlation now supports a more specific causal chain than the initial incident classification:

1. **The live path was allowed to write an unbounded stream into the real DevTools console.** In `Active/O8.13/shards/shard-a.js`, `Log.say` and `Log.info` call `console.debug` for ordinary progress/status lines. The per-line truncation is not a cumulative event or byte limit; the small queue limit applies only to queued diagnostics. The supplied log confirms the resulting failure at the sink: an attempted `console-history` value of about 62 MB was rejected while an existing value was already about 52 MB.
2. **The desktop/stream workers entered Discord’s real running-game pipeline.** In `Active/O8.13/shards/shard-e.js`, the workers hook the running-game accessors, construct synthetic process/game records, dispatch the decoded `RUNNING_GAMES_CHANGE` event, and later dispatch removal during cleanup. This is not an isolated fake dispatcher.
3. **The log shows the host processing those records, not ignoring them.** Discord classified synthetic records as non-games, then still ran `OverlayRenderStore`, `OverlayBridgeStore`, overlay-method updates, untracking, and `RunningGameHeartbeatManager` performance-snapshot attempts. The repeated long-task warnings are consistent with this extra host event/IPC/UI work.
4. **Discord’s own module exceptions were the terminal application fault.** The undefined `GAME_SERVER_SUBSCRIPTION_CHECKOUT` error occurred after the activity/IPC churn, and the later undefined `$` error occurred during navigation after the renderer was already heavily stalled. The log cannot prove whether the first Discord exception is a Discord rollout defect or a path reached by the synthetic activity, but it does show that O8.13 exposed the host to that path.

**Conclusion:** the best-supported root cause is **unsafe live host integration by the synthetic running-game/overlay path, amplified by unbounded console persistence**. The `GAME_SERVER_SUBSCRIPTION_CHECKOUT` and `$` exceptions are downstream Discord-side failures, not evidence that a single O8.13 expression directly crashed a native process. This is a design-level failure of the live-test boundary, not a confirmed native Discord crash.

## Resolution tracked as FaC-17

The resolution is recorded in `Active/O8.14/O8.14-FAC-CC-PLAN.md` and assigned to existing **CC-03**. The first wording was intentionally conservative but too broad: removing the live activity signal outright would break the primary desktop/stream completion path. FaC-17 is therefore **primary-preserving**. It keeps the required activity signal behind a narrowly scoped, single-flight adapter, separates it from optional overlay/telemetry/UI work, requires a private simulated adapter for harness runs, and rejects a live mode if that signal cannot be provided without uncontrolled host churn. It also replaces direct repetitive console output with a bounded diagnostic sink that records capped counters/summaries without using persisted DevTools history as the measurement store.

Cleanup must verify that hooks, listeners, timers, subscriptions, and synthetic activity are gone after completion or abort, while the approved adapter mode still demonstrates the primary desktop/stream behavior. This resolution is documented for the next O8.14 CC; it does not patch or reopen O8.13-r3.

## Primary-path correction

The source and harness make the compatibility boundary explicit: `shard-e.js` uses the synthetic activity path for desktop/stream workers, and the existing simulated S1 scenario requires a `RUNNING_GAMES_CHANGE` dispatch while proving both desktop and stream completion. Therefore “remove all synthetic activity” is not an acceptable fix. The fix is to contain and measure the signal, not to delete the primary feature.

## Immediate containment

1. Stop live testing and do not paste the release again.
2. Fully reload/quit Discord so temporary hooks and listeners cannot survive in the current renderer. Reopen it without the script.
3. Close DevTools or clear its persisted console history through the DevTools UI before another unrelated diagnostic session. Do not delete Discord account/application storage casually.
4. Preserve the supplied log and, if available, the Discord app/browser version, operating system, renderer crash report, and the exact time of the incident.
5. If the same generic crash appears in a clean Discord session with no script, record it as a Discord control failure rather than a release failure.

## Required diagnostic gate before any real-host test or promotion

- Reproduce only in a disposable, offline/simulated harness first.
- Add bounded log capture with a hard event/byte cap; console output must not be the measurement store.
- Measure host event volume, listener/timer count, retained heap, and main-thread task duration.
- Treat synthetic running-game/overlay integration as a separate risk item; do not combine it with a pipeline or obfuscation revision.
- Compare clean-control, activity-off, minimally scoped adapter, and current-adapter candidates without touching O8.13-r3 bytes.
- Obtain a renderer/native crash artifact before calling this a native Discord crash.

This record is an incident hold, not a release diagnosis or a permission to patch the frozen line.
