# O8.14 — FaC / CC implementation plan

**Status:** corrected terminology and implementation list, 2026-09-19.  
**O8.14 scope:** F2–F9 owner-side changes, alternate representation layers, CAR-M, R2-08, and conditional R2-09/R2-10.  
**O8.13-r3:** remains frozen and is the regression baseline.

## Terminology

- **FaC — Feature and Change:** one concrete feature or source/design change to implement.
- **CC — Compiled Change:** a compiled change set that combines named FaCs into one attributable
  build output. A CC is not another name for an individual FaC.
- **Verification gates:** tests and measurements applied to a CC. They are not FaCs.

The previous O8.14 draft used “FaC” as if it meant acceptance criterion and “CC” as if it meant
change control. That was wrong. This document uses the project's established meaning.

## O8.14 constraints

- No O8.14 work overwrites O8.13-r3.
- No change is promoted to a live directory until its CC is independently verified.
- The mandatory regression baseline remains 25/25, corrected 16/16, 43/0, manifest parity,
  self-identifying names, and successful release verification.
- A historical 14/16 result must remain historical. It must never be silently relabeled as a new
  security result.
- Measured memory, transmission, footprint, or analysis-cost improvements are welcome, but not at
  the expense of the regression baseline.
- The normal path must not add telemetry, DOM/CSSOM work, GPU work, or persistent buffers merely to
  make a decoy exist.

## FaCs — Features and Changes

### FaC-01 — R2-06 pipeline-template neutralization

Remove or replace readable pipeline labels that provide a free structural map. Keep diagnostics
contentless enough to preserve level-2 usefulness without exposing the construction vocabulary.
Measure emitted bytes, log bytes, and behavior before and after.

### FaC-02 — F2 evaluator-boundary census

Add measurement instrumentation around the existing decode-to-execution boundary: evaluator hooks,
decoded-buffer lifetime, allocation, abort, and cleanup. This first FaC is measurement-first and does
not replace the current execution path.

### FaC-03 — F3 host-call/transmission census

Record the current host method, route, body shape, timing, byte count, and stop conditions. Preserve
the current tested behavior in the first O8.14 CC. Later FaCs may remove or restrict calls, but may
not add unallowlisted host activity or falsify telemetry.

### FaC-04 — F4 deterministic branch census

Add a private deterministic matrix for real, fallback, honey, and malformed branches. It records
branch identity, attempted host I/O, allocations, cleanup, and result—not just console output.

### FaC-05 — F6 global-surface reduction

Remove unnecessary global unlock surfaces, close over state where possible, and ensure test-only gates
are clearly non-sensitive. This FaC may not add authority, storage/cookie access, or new globals.

### FaC-06 — F7 allocation and cleanup guardrails

Bound decoded length before allocation, apply abort/time limits, and restore listeners, timers, and
host hooks in cleanup paths. The change must be measured against the O8.14 baseline.

### FaC-07 — F8 message-surface minimization

Minimize or remove same-origin coordination where direct local state is sufficient. Use a small
explicit schema and do not send sensitive values through the channel.

### FaC-08 — R2-08 extended shard/module separation

Separate host/store adapter, scheduler/progress state machine, transport allowlist, cleanup, and
telemetry plumbing. Evaluate the extended H split beyond `shard-e`. No new endpoint, storage/cookie
access, global export, or dynamic code generation may be introduced.

### FaC-09 — VM-S: the one custom shard VM

Use the project's own compact VM on selected shard/core paths where it replaces ordinary source
structure. VM-S is the only VM assumed in the O8.14 plan. It must have explicit opcode, length, time,
allocation, and host-capability limits.

VM-S is not a second JavaScript obfuscator and is not automatically applied to the whole payload.
The bulk remains ordinary code/data unless a later FaC proves a different choice is useful.

### FaC-10 — bounded non-executable data parser

Add a finite, linear-time parser for a small data grammar. This is a **parser/codec**, not a second
VM. It may decode records used by VM-S or an outer shell, but it may not evaluate arbitrary source or
obtain ambient host capability.

### FaC-11 — CSS/HTML serialized decoy layer

Represent a bounded CSS/HTML decoy or metadata record as serialized data in an existing decoy/carrier
budget. The first version must not create DOM/CSSOM objects on the normal path. It must replace bytes,
not simply append bytes, if static footprint is to remain neutral.

If a future CC deliberately parses the record, that is a separate measured variant with explicit
DOM/CSSOM and retained-heap gates. It is not assumed to be footprint-free.

### FaC-12 — XML/XSLT serialized decoy layer

Represent a bounded XML/XSLT-shaped decoy or metadata record as serialized data in an existing
carrier/decoy budget. The first version must not invoke `DOMParser` or `XSLTProcessor` on the normal
path. A parsed XSLT/XML variant is a separate compatibility experiment, not part of the default
outer shell.

### FaC-13 — WebGL/GLSL serialized decoy layer

Represent a bounded shader-shaped decoy or metadata record without requiring a WebGL context on the
normal path. A true shader execution variant is optional research only and must not be required for
correctness, startup, or extraction.

### FaC-14 — CAR-M carrier conversion

Test 4-bit→2-bit and viable alternatives on non-executable data. Measure capacity, PSNR, maximum
channel delta, corruption tolerance, decode compatibility, peak/retained memory, and repeated
extraction. Same-cover naive 2-bit conversion remains over capacity: 3,483,480 required symbols
versus 2,260,322 positions.

### FaC-15 — R2-10 true four-way carrier

Test `R9R0..R9R3` as an offline codec change first, then separately test delivery/loader integration.
Do not combine it with CAR-M in the first implementation.

### FaC-16 — O8.14 release/provenance update

Create self-identifying O8.14 names, current manifests, provenance, verifier pins, and explicit
experimental/candidate/live status. The O8.13 live mirror remains untouched.

### FaC-17 — primary-preserving live-host activity and diagnostic-pressure containment

Close the live-test boundary exposed by the O8.13-r3 incident **without removing the primary task
behavior**. Desktop/stream completion currently depends on an activity signal, so FaC-17 must not
silently disable that path. Instead, place the required signal behind one narrowly scoped,
single-flight host-activity adapter; keep it separate from optional overlay, heartbeat, telemetry,
and UI surfaces; and minimize the lifecycle and record surface exposed to the host. A private
simulated adapter remains mandatory for harness work. If the host cannot provide the primary signal
without broad overlay/IPC churn, that mode must be marked not live-eligible rather than replaced by
a silent non-working path.

Diagnostic output must use a bounded event/byte sink with counters and summaries, not repetitive
unbounded `console.debug` output or persisted DevTools console history as the measurement store.

Cleanup must be explicit and observable: restore every host hook, remove listeners, clear timers,
withdraw synthetic records, and verify that no active task, subscription, or overlay-facing record
remains before the run is considered complete. The primary completion path must remain functional in
the simulated and approved adapter modes.

Acceptance requires separate clean-control, activity-off, minimally scoped adapter, and current
adapter comparisons; a passing primary desktop/stream behavior check; bounded log capture; host
event/IPC activity accounting; main-thread task-duration observations; retained-heap comparison;
and zero residual hooks/listeners/timers/synthetic activity at teardown. The result is candidate-only
until those gates pass. FaC-17 does not modify O8.13-r3.

## Non-JavaScript layer placement and footprint rule

The four non-JavaScript representation surfaces are treated as **serialized layers first**, not as
four new runtime engines:

```text
carrier/stego
  -> serialized layer envelope
       -> CSS/HTML record
       -> XML/XSLT record
       -> GLSL record
       -> VM-S/data records
  -> existing selected shard/core path
```

The envelope may be placed in either of the two intended positions:

- **below stego:** as a carrier-side record that the stego extraction path delivers;
- **above stego:** as an outer-shell record surrounding the extracted stream.

The placement is a per-FaC decision and must not be duplicated by copying the same data into both
locations.

For the no-footprint requirement, the first implementation is **budget-neutral substitution**:
replace existing decoy/metadata bytes with the alternate representation rather than appending a new
payload. The normal path does not parse CSS, XML, XSLT, HTML, or GLSL, so it adds no DOM/CSSOM/GPU
footprint. A runtime-parsed variant is possible, but it cannot honestly be called zero-footprint and
must receive its own measurements.

This gives each surface its own representation method without pretending that browser parsers are
free or that serialized decoy text is equivalent to a separate execution engine.

### Combined CC-02+03 implementation pass

By operator authorization, CC-02 and CC-03 may share one candidate tree and verification run at
`Active/O8.14/CC-02-03/`. The pass combines FaC-01 with FaC-05, FaC-06, FaC-07, FaC-16, and
FaC-17, but keeps FaC-level measurements and failure attribution separate. It is an implementation
convenience, not a new promotion category: both CC-02 and CC-03 gates must pass, O8.13-r3 remains
frozen, and no live promotion follows from the combined run.

### CC-04 / CC-05 candidate status

The next two CCs are implemented as separate candidate trees:

- `Active/O8.14/CC-04-VM-S/` — bounded VM-S candidate; simulated gate PASS.
- `Active/O8.14/CC-05-Parser/` — bounded non-executable parser candidate built on CC-04; simulated gate PASS.

Both preserve the primary S1 behavior and remain candidate-only. Neither is live-eligible until the
real-host renderer/memory comparison and full OTO/obfuscation review pass.

### CC-06 / CC-07 / CC-08 candidate status

The serialized non-JavaScript layers are now implemented as separate candidate trees:

- `Active/O8.14/CC-06-CSS-HTML/` — bounded CSS/HTML serialized record; simulated PASS.
- `Active/O8.14/CC-07-XML-XSLT/` — bounded XML/XSLT serialized record; simulated PASS.
- `Active/O8.14/CC-08-GLSL/` — bounded GLSL serialized record; simulated PASS.

Each substitutes one exactly 731-byte existing `shard-n2.js` budget slot. The normal path stores a
bounded string and checksum only; it does not invoke a markup parser, DOM/CSSOM API, WebGL context,
shader compiler, evaluator, network route, or second VM. All preserve S1 desktop/stream completion.
They remain candidate-only and require the full OTO, renderer, heap, cleanup, and real-host gates.

### CC-09 candidate status

CC-09 / R2-08 is implemented separately at `Active/O8.14/CC-09-R2-08/` and passes simulated
verification. It adds an extended `shard-h.js` before `shard-e.js`, with private host, store,
transport, scheduler, cleanup, and bounded telemetry adapters under `_0xmod.r2`. The engine routes
its dispatcher, store values, scheduler sleep, transport calls, cleanup registration, and telemetry
through those adapters. The candidate adds no global, endpoint, storage/cookie access, message
channel, dynamic-code path, or second VM, and preserves the S1 desktop/stream scenario. It remains
candidate-only pending full OTO, renderer, heap, cleanup, and real-host gates.

### CC-10 / CC-11 / CC-12 candidate status

The carrier changes are kept as three separate candidate trees:

- `Active/O8.14/CC-10-CAR-M/` — CAR-M laboratory revision; simulated laboratory PASS.
- `Active/O8.14/CC-11-R2-10A/` — offline R9R0..R9R3 true-four-way codec revision; simulated PASS.
- `Active/O8.14/CC-12-R2-10B/` — bounded delivery/loader integration over a copied R2-10A codec; simulated PASS.

CC-10 uses non-executable serialized metadata only. Its same-cover naive two-bit test preserves the
capacity result of 3,483,480 payload symbols versus 2,260,322 positions and rejects that attempt;
the measured viable alternative is a separate expanded carrier. CC-11 is offline only and uses four
independent tagged lanes with bounded lengths and per-lane CRCs. CC-12 keeps delivery injected and
caller-allowlisted, adds a bounded envelope parser and idempotent cleanup, and introduces no fetch,
new host route, global, dynamic-code path, or unallowlisted transmission. CC-12 also preserves the
S1 desktop/stream regression through the existing candidate harness. A separate security-hardening
run now rejects oversized/truncated/malformed inputs, unsafe routes, sender exceptions, closed-loader
use, and dynamic/network capability additions for the three candidates. All three remain
candidate-only pending full OTO, renderer, heap, cleanup, real-host, and explicit GO LIVE gates.
### CC-13 / CC-14 candidate status

CC-13 is implemented at `Active/O8.14/CC-13-Pairwise/` and passes pairwise verification. It builds
three attributable runtime profiles: CC-09 extended H plus exactly one of the mutually exclusive
CC-06/07/08 serialized `n2` layers. It records 55 pairwise rows, keeps CAR-M isolated from R2-10,
and does not select a promotion profile.

CC-14 is implemented at `Active/O8.14/CC-14-Candidate-Compilation/` and passes candidate compilation
verification. It indexes all approved FaCs from CC-01 through CC-13, copies the three CC-13 runtime
profiles, and carries the isolated CC-10/11/12 component artifacts with hashes. It is a
provenance-first multi-profile compilation: no runtime profile is canonical, no CAR-M/R2-10
combined carrier is made, and it is not a release package. Both remain candidate-only; CC-15 is not
started.

## Compatibility and regression gates for every CC

## Compatibility and regression gates for every CC

- 25/25 battery;
- corrected 16/16 verification, with its harness correction documented;
- stego 43/0 result where the CC includes a carrier/runner;
- no new host route or unallowlisted data transmission;
- no unexplained increase in peak/retained heap;
- no leaked listeners, timers, hooks, or globals;
- malformed-input and abort behavior remains bounded;
- manifest/provenance is current;
- TUBE behavior is checked after every CC that changes the outer shell, VM-S, parser, carrier, or
  shard structure.

## Corrected VM answer

There are **not two planned VMs**.

- **VM-S** is the one custom shard/core VM already contemplated by the project.
- **FaC-10** is a bounded data parser/codec, not another VM.
- A second VM would require a new, explicit FaC and would not be introduced by implication.

The previous draft's wording made the parser and VM sound like two inevitable VM systems. That was
incorrect and is corrected here.

## Implementation order

1. CC-01 / O8.14-B0 baseline.
2. CC-03, including FaC-17 containment, before any live-host test or promotion review.
3. CC-02, if the template cleanup remains desirable and the incident diagnostic gate is clear.
4. CC-04 VM-S measurement/revision.
5. CC-05 bounded parser.
6. CC-09 R2-08 modularization.
7. CC-10 CAR-M laboratory revision in a separate carrier path.
8. CC-06, CC-07, and CC-08 serialized non-JavaScript decoys independently.
9. CC-11, then conditional CC-12 for R2-10.
10. CC-13 pairwise compatibility.
11. CC-14 candidate compilation.
12. CC-15 only after explicit go-live authorization.

The previous R2-06 + CAR-M + R2-08 combined rebuild failure is specifically prevented by this
FaC/CC separation.
