## What the Lazy Forcer is for
Discord's webpack runtime keeps two tables on the module function: `_0x2.c` = **instantiated**
modules (factories already executed), `_0x2.m` = **definitions** (factories not yet run; the client
instantiates lazily). Pocket discovery only scans the instantiated cache. In the O7.34-era client the
cache was tiny (~102 entries) vs ~8.4k definitions, so required stores sometimes simply were not
instantiated yet → pockets missing. The forcer walks `_0x2.m`, finds definitions whose **source text**
contains one of the decoded target method names, and executes that factory `_0x2(id)` so the module
lands in `_0x2.c` and the scan can find it.

History: O7.35 tried this (forced 232 → cache 2,112) and pockets still weren't found — the real fix
was push-return capture; arbitrary module execution has side effects, so it was excluded from the
deterministic O7.38–O7.41 line. O8.x reintroduced it bounded (≤50, skip already-instantiated,
try/catch each, cacheBefore/After diag). Live logs show it working: `Lazy Force {forcedCount: 50,
cacheBefore: 8292, cacheAfter: 8427, cacheDelta: 135}`.

## Can it run after the juggler?
Yes — and it already does. Order in source: juggler decodes the 23 constants (top of the async
scope) → runtime capture → **forcer** → discovery scan → gate. It must be after the decoder because
the matcher greps module sources for *plaintext* method names; before decoding, targets are
ciphertext and zero modules would match. J-3 keeps the forcer in exactly that position, unchanged
from stable. (If you ever want an A/B test of the background-404 theory, setting the cap to 0 is a
one-line change.)

## Faults found in J-1 / J-2 (must-avoid list)

### J-1 (original integration)
- **F1 — Deep Scanner replaced the proven scan.** It recursively inspects every export and every
  child key of ~8k modules, and binds `_0x8`/`_0x9` under extra predicates (`GoogleHas(obj,
  "subscribe")`, `"post"`). That can select *different* flux/http objects than stable's slot scan
  (`exA/exAy/exh/exBo`) → behavioral drift and a plausible (unconfirmed) source of the live failure.
  Rule: **keep stable's slot scan + interface validation** (J-3 does).
- **F2 — Inert env-probe path.** All 23 arrays shipped `ep=[0]`, so the "polymorphic" environment
  probe never executes; the 20-line matrix is dead complexity. If it were ever populated with
  env-derived keys, a client update would silently break decoding (the gist's own risk note).
  Rule: deterministic fallback is the effective path; arrays are **verified to decode 22/22** before
  shipping (J-3: 23/23 identical to stable plaintexts).
- **F3 — Misdiagnosed 404.** The gist's conclusion blamed `GoogleRoutes.videoProgress/applications`,
  but the logged URL `https://discord.com/[object%20Object]` carries **no** `/quests/` or
  `/applications/` prefix — no GoogleRoutes builder can produce it. Rule: guard at the net layer and
  diag non-string URLs wherever they originate (J-3 does, via GoogleId + transport guard).

### J-2 (fix built on J-1)
- **F4 — Painted over J-1.** Inherited F1/F2, so its live 404 result could never isolate the cause.
  Rule: **rebuild from stable** (J-3 does; deltas vs stable are exactly three subsystems, listed below).
- **F5 — Guards only cover our own three call sites.** Live J-2 run: no `URL id`/`HTTP url` diag
  fired yet the 404 persisted during the boot idle delay, with Discord-internal frames
  (`620620….js:12` ×4, `apply`, `setTimeout`) — i.e., the failing request never enters `GoogleCall`.
  Best current explanation: a Discord-internal scheduled GET with an object URL (background noise),
  not a script request. J-3 keeps the guards (correct for our calls) but does not claim to silence
  Discord-internal noise. **A/B test:** run stable O8.2 once and check whether the same console 404
  appears there too — if yes, it is environmental, not a J-delta.
