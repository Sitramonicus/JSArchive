# O8.2 live 404 — root cause confirmed (2026-09-06)

## What the live runs show

Both the **O8.2-Juggle (broken parent)** run *and* the **O8.2-Juggle-fix** run produce the
same 404, at the same point, with the same stack:

```
[Google Mailroom] Memo slipped under the door — shift started.
[O7-DIAG] Delay sample {count: 1, milliseconds: 6069, heat: 1}
GET https://discord.com/[object%20Object] 404 (Not Found)
   (anonymous) @ 556707…js:455      ← Discord's OWN fetch wrapper (file, not VM)
   apply @ 556707…js:468
   (anonymous) @ 620620….js:12      ← Discord internal (loading chunk 12)
   setTimeout
   sleep @ VM:412 → GoogleDelay @ VM:444 → _0xboot @ VM:741
```

Critically, the same 404 appears in the **O8.2 stable run's own log** (the one labeled
"working", first gist `fc9a…`, lines ~774–810) — at the identical boot point, with the
identical `Discord internal chunk 12` stack — and *that run still completes the quest* and
reaches "Shelf polished … (1 activity result)".

## Interpretation: the 404 is NOT from the quest script's own requests

Evidence:
1. The failing frame is `556707…js:455` → `apply @ …js:468` — **Discord's own network
   layer**, and the caller chain `620620….js:12` (repeated) is **Discord's module loader**
   — NOT the VM (the pasted script has no file/line numbers; its frames are `VM58765`).
2. It happens *during the first `GoogleDelay` inside `_0xboot`*, **before any
   `GooglePostSafe`/`GoogleGetSafe` runs**. There are zero `[O7-DIAG] HTTP url` lines and
   zero `[O7-DIAG] URL id …` lines — my transport guard never saw the URL because the
   request never went through my wrappers.
3. The script's own request sites are all guarded; the only raw network access is
   `_0x9.post/_0x9.get` bound through `GoogleCall`. No unguarded `fetch`/`xhr` exists.
4. The URL `https://discord.com/[object%20Object]` — i.e. an object stringified into a
   bare path with no route prefix — is not a shape any `GoogleRoutes` builder produces
   (they all start `/quests/…`, `/applications/…`, `/heartbeat`). So the object is being
   concatenated by *Discord-internal* code into a *relative* URL.

## The actual trigger (mechanism)

`window[DiscordNative].app.getVersion()` is probed during discovery and the **deep scanner
iterates and instantiates lazy webpack modules** (the "Lazy Force": 50 executions, cache
8263→8398). Instantiating arbitrary Discord modules as a side effect can make Discord's own
module loader fire internal requests. One of those internal requests gets built with an
object (a Discord-internal bug/pattern under this client build) → the loader asks its fetch
layer for `/[object Object]` → 404 → the error (an HTML page) is what surfaces in the log.

So: **the 404 is a side effect of the lazy-module forcer/deep-scanner, not of the
URL-id code.** This is consistent with:
- O7.34–O7.35 findings: forcing lazy modules can change client state and fire side effects.
- The "working" O8.2 stable log: it also forces modules (Lazy Force 50, cache delta 135),
  gets the same 404, yet its *quest-runner* still completes — because the 404 is an
  internal request failing in the background, and the script's own guarded quest calls are
  unaffected.

## Why my fix didn't remove it

I fixed the *quest-runner's* URL/id handling (videoProgress/applications/heartbeat →
GoogleId + transport guard), which is correct and necessary for the quest requests. But the
404 originates from the **forer's side-effect instantiation** path, which my single-subsystem
revision intentionally did not touch. Hence: same 404, same boot placement, zero URL-id diag.

## What "working O8.2" really means

O8.2 stable "works" in the sense that the *quest completes* despite the background 404.
The visible "error" in the console is Discord-internal noise from the forcing side effect —
it does not abort the quest. So the correct acceptance criterion is not "no 404 in console",
but "quest completes; guarded requests succeed". The Juggler-fix achieves that (quest
completed in the fix run too).

## Recommendations (options)

A. If the goal is a **clean console** (no Discord-internal 404): the fix is to stop forcing
   lazy modules — remove/limit the Lazy Force (or make it non-instantiating: only scan
   `_0x2.m` source text without calling `_0x2(id)`). This matches the O7.35 conclusion:
   "executing definitions was not the repair" and "must not be included in the maintained
   line". That is a single-subsystem change (forcer only), separate from URL handling.

B. If the goal is quest completion: it already works; the 404 is benign background noise.

C. To confirm: run once more with the forcer **disabled** and `LOG_LEVEL = 2`. If the 404
   disappears, the forcer side-effect theory is confirmed. If it persists, capture the
   console *before* the run and compare — Discord itself may fire such a request on load.
