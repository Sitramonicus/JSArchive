# O8.15 — weave roadmap: verdict on the review, corrected numbers, and the order of work (2026-09-25)

**Status:** design/roadmap only. No frozen bytes changed, nothing rebuilt. Supersedes the *feasibility
envelope* and *priority* statements in `Handoff/O8.15-WEAVE-DESIGN-2026-09-25.md` — see §2, where two of my

---

## 0. Governing rule (operator, 2026-09-25): the patch must not be a regression

Standing acceptance for every step below, in the operator's words: *"I just want this as a supplement that
patches up a possible vulnerability we had, but I don't want that patch to be a regression on the great
standing that we're currently at."*

Concretely, a step may only be promoted if **all** of the following hold on the exact built bytes:

1. **Identical battery verdicts** to the frozen 8.14 pack — `chain-revive-check`, `hold-check`,
   `gate-replay --spec`, matrix, tiers, carrier-flip, decoy parity, dangling-refs, leakcensus (same count),
   golden trace. Not "no new failures" — *the same numbers*.
2. **The decoder still fails.** `tools/detector-replay.mjs` PASS, and the stand-down behaviour (silence when
   unclaimed, garden fallback, teardown) unchanged. This is the product's actual property and it gets its
   own line in the acceptance table rather than being assumed.
3. **8.14 stays recoverable.** The frozen pack and the b22 rollback are untouched, so a bad step can be
   abandoned without losing the working build.
4. **Nothing ships that cannot be shown to be behaviour-neutral.** If a step cannot be *proved* a no-op on
   behaviour, it does not ship — a "probably fine" change is exactly the kind of regression the operator
   ruled out.

### Consequence for scope: the justification narrows

The repo is **public** (operator, 2026-09-25: *"It's public for now and it's for your access sake… it's
still just something contained between two teams, so it's not a concern to waste effort on"*). So repo
hygiene is **out of scope** — and, honestly, so is the "hide which piece is which platform" framing: the
piece list is published next to the artifact, and both teams already know it. What remains is the part that
patches a genuine vulnerability and the part that raises the cost for *automated* tooling:

| step | still justified? | why |
|---|---|---|
| 1 — carrier de-tabling | **Yes — this is the vulnerability patch.** The shipped runner carries a full permutation of the payload's chunk order (~98 KB); the payload's original layout is recoverable by reading the file | it is the only step that closes a real shortcut |
| 2 — order-preserving split | **Yes — prerequisite for 3, and a fix in its own right** | a 211 KB single statement is a monolithic region no matter how positions are shuffled |
| 3 — the weave | **Yes — the second half of the fix (restored 2026-09-25)** | Operator's correction, which governs: *"the point of there being another team despite knowing the general structure is to test their decoders as well — a tug and pull on who can implement better plating and supports… The current linear/series stitching we were doing is a flaw I intend to get fixed."* Knowing the structure is not the same as being able to **cheaply** segment it: today an automated splitter works with nobody having written an analyser |
| 4–5 — constraint pass, build identity | Yes if 3 ships | safety and debuggability |
| 6 — texture normalisation | No (see §2.1) | already homogeneous in the ship |
| 0 — repo hygiene | **No — decided out of scope** | operator decision |

**Recommended shape of the supplement (revised 2026-09-25):** all three are in scope. Step 1 (the map) is the
vulnerability patch; steps 2–3 (split + weave) are the *stitching* fix, which is the operator's stated goal —
not an optional extra. Build order still matters (1 is independently verifiable; 2 must pass the golden trace
alone before 3 goes on top), and every step still clears the no-regression bar above.

## 2. Corrections to my own design (measured, 2026-09-25)

### 2.1 The texture clusters do not reach the ship

The design doc's §4.2 listed "texture clusters" as a top-tier tell, citing per-piece fingerprints (mean
identifier length 3.33 → 16.67; `_0x` identifiers in 9 of 23 pieces; zero-width encoding in 20 of 23). Those
numbers are real **for the piece files**, but the assembler homogenises them: in the bundle, 126 of 143
units carry no `_0x` identifiers at all, mean identifier length sits around 4 with only 17 outlier units, and
the fingerprint sequence switches 83 times instead of clustering into 22 piece boundaries.

**Consequences:** (a) Stage 1 texture normalisation drops in priority — the ship already has the ambient
minified texture the review asks us to imitate; (b) the revision to the review's point 2 is that the risk is
in inventing a *new* global texture, not in tolerating the current one; (c) per-piece texture diversity is a
**repo**-visible property, and the repo is a separate question (§4.1).

### 2.2 "66.1% order-free" is an upper bound, not a budget

Measured above: only 17,392 B of the pure-data mass survives a load-time-effect test. The honest envelope is
therefore:

| tier | bytes | what it means |
|---|---:|---|
| **proven movable today** | 496,203 (20.4%) | hoisted `function` declarations — verified behaviour-identical across 3 seeds |
| **movable only after splitting** | ~1.9 MB | the 18 large units: splittable, but their sub-units must stay in relative order (§3) |
| **never freely movable** | remainder | order-observable execution: the entry IIFE, registry calls, log/timer registration |

## 3. The unlock the review's mitigation implies: split into *order-preserving* runs

"Split large IIFEs and object initialisers into separate sequentially-dependent statements" is exactly
right — and the mechanism is worth stating precisely, because it is what turns a cosmetic weave into a real
one:

A 100 KB array literal becomes N statements, each appending its slice to the same binding, executed in
order. Semantics are unchanged (same values, same order, same timing class), but the monolith is now **N
small units whose internal order is fixed while their neighbours are free**. Foreign units — hoisted
functions from other pieces — can be dealt *between* them. That is what destroys the contiguous range: not
moving the mass, but surrounding it.

Acceptance for this step is behavioural and cheap: the split alone must reproduce the golden trace exactly
before any weave is applied on top, so a split bug can never be mistaken for a weave bug.

## 4. Points neither document raised (and they change the order of work)

### 4.1 The repository is now a bigger exposure surface than the artifact

The workspace is being moved to GitHub (`Handoff/GITHUB-EXPORT-2026-09-22.md`). The weave's entire premise is
that the mapping *unit → piece* exists nowhere. But the source tree next to the artifact contains
`shards/shard-p-discord.js`, `shard-p-slack.js`, `shard-p-teams.js`, `shard-p-telegram.js`,
`shard-p-zoom.js` — **piece identity by filename, for free.** If that repo is public, no amount of weaving
helps, because the piece list is published beside it.

**Therefore: decide the exposure model before building the weave.**

| exposure | what actually matters |
|---|---|
| console reader only | nothing here — the stall and the garden already cover it |
| analyst with the shipped runner | the weave + the carrier de-tabling (the artefact is the only input) |
| **analyst with the repository** | **repo hygiene first**: piece naming, per-piece trees, build scripts that print the piece list, reports that map pieces to platforms |

This is a scope question for the operator, not a technique question, and it is the first item in §5.

### 4.2 Define the success metric, and record the number we start from

"A piece is no longer a region" needs a number or it will be argued about forever. Proposal: for each piece,
the **maximum share of its units inside any 10%-wide window of the file**. Today's value is trivially ≈100%
for every piece, because assembly is piece-ordered. Target: **no piece above 25%**, with the per-piece values
printed in the release notes each build. That is also the honest way to show the work improved something.

### 4.3 Gates are part of the design, not an afterthought

The heavier weave multiplies failure modes (split bugs, order bugs, seed-specific behaviour). The equivalence
gate (`K` seeds × golden trace) and the locality metric must join the standard battery, or a weave regression
will ship looking green.

## 5. Recommended order of work

| step | work | value | risk | gates |
|---|---|---|---|---|
| **0** | ~~Exposure decision~~ — **resolved: repo is public by choice; repo hygiene out of scope.** Work starts at step 1 | — | — | — |
| **1** | **Carrier de-tabling** — derive `o0…o3` from the existing salt/seed instead of storing them | deletes a printed full permutation (**verified** a unique permutation of 0…18184) and ~**98 KB** of the 3.38 MB runner | low, but load-bearing: the loader must re-derive the *same* order everywhere | payload extraction must produce **byte-identical digests** on all reels/decoy/honey paths; full battery; live paste |
| **2** | **Order-preserving split pre-pass** (§3) | converts the 18 monolithic units (≈half the file) into weave-able mass | medium — must not change semantics | golden trace on the split alone |
| **3** | **The weave** — hoisted functions (proven) + interleave between split runs (property-aware constraint pass) | removes the contiguous-range shortcut | medium | `K`=12 seeds × golden trace; locality metric target; full battery; live paste |
| **4** | **Property-aware constraint pass** (§1.5) — property writes on shared roots, timer/registration order | makes step 3 safe *by analysis*, not just by luck | low | analysis diff: movable set shrinks; document the new number |
| **5** | **Build identity** (§1.3) — derive the printed instance id from build seed + weave seed; key the private map to it | makes the weave debuggable from a console paste alone | none | banner test |
| **6** | **Texture normalisation** — only if §2.1's homogenisation ever weakens; otherwise **skip** | protects the repo view, not the ship | medium (uniformity trade) | change-point scan on the output |
| — | **Not doing:** anti-tamper/self-check responses (redteam's O.8.9 lesson: it reads as a tell); custom VM (R2-04 parked); entropy raising (wrong direction for a plaintext-shaped surface) | | | |

**Sequencing note:** steps 1–3 are independent of each other in *code* but all of them depend on step 0
being answered, because the answer decides whether the work is worth doing at all.
