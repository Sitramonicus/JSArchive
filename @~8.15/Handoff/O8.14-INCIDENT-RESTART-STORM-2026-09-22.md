## Root cause — three defects, two of them mine from the last two hours

**Defect 1 — `_0slow is not defined` (a syntax-level regression in the retry).**
The claim-gated retry loop ticked as: `const _0slow = _0xtries++ >= 30;` … `setTimeout(_0xtick, 5000)`.
The timer double reads `_0slow` **outside** the block where it was declared — so every tick that reached
the timer threw a `ReferenceError` instead of rescheduling. In a build where this branch is dead code it
is invisible; the moment a claim walks into it, the worker dies mid-run and the session closes early.
The `F5 whilst in console` label change had also removed the only line that would have printed in that
path, so the failure was silent apart from the console's own error. Fixed: the tick's locals live in the
tick, `_0slow` is computed from state (`_0xtries >= 30`), no cross-scope reads, and the claim-gated slow
tail is gone entirely (it was the thing that made a dead session look busy).

**Defect 2 — the finished session is relaunched every 5 s (the storm).**
`phase-st` → `Last call` → `Session closed` in a loop is the worker being **started again and again**.
The retry's old guard was `if (_0xkill || _0xtries++ >= 30 || _0st === 'live') return;` — it never
checked `closed`. A finished session sets `_0xchain = 'closed'`, but a *claim* leaves `_0xclaimed` true,
so every tick saw "claimed + venue ready" and called `begin()` on a session that had already ended. Each
`begin()` produced one `phase-st`, one "Last call", one "Session closed", and another closed chain.
Fixed: the tick ends on `closed` **and** on `live` (and on `_0xkill`, and after 30 fast ticks). A finished
session is reopened by a **new claim**, which revives directly — not by the retry.

**Defect 3 — `GoogleRelease()` is one-shot and it ABORTS the shared controller (the actual amplifier).**
This is the part that made it permanent rather than cosmetic. `GoogleRelease()` latches (`released`) and
calls `controller.abort()`. `e2`/`e3`/`e4` all captured that same `signal` **at load**, so after a release
every later piece sees `signal.aborted === true` from its first line: any revived session is born dead and
the worker bails at its first `if (signal.aborted)` check. Pass 3's `_0slow` error is a *symptom of the
same walk*: the worker was being entered on a page that could no longer run anything.

Two consequences were shipped without thinking them through, and both are now fixed:

* the **no-chores** path (`e2`) called `GoogleRelease()` — so a page whose ledger came back empty was
  *bricked for good*: "nothing to do" was treated as "session over, tear the page down". That is exactly
  the behaviour a reloaded, running client hits, and it is what your pass 1 did at `+10.2 s`.
* the **finished-session** `finally` called `GoogleRelease()` too, so *every* completed session left the
  page unable to run again — the opposite of what build 19/20 claimed to fix ("a new claim reopens it").

Fixed in both places, plus a guard so this can never silently return: **a released page refuses to
start a session** (`begin()` returns `false`, the worker head returns before claiming `live`), and the
claim report now says so — `chain {"state":"scanned","ok":false,"released":true,…}` instead of a
confident `ok:true`.

## Why my own checks did not catch it (the part that matters)

* **C8 asserted the wrong thing.** It required "a claim starts the worker", and it *passed* on the broken
  build precisely because the broken code started the worker **unconditionally** — including on a page
  that could not run. A test that the bug satisfies is not a test. C8 now: (a) requires the worker to be
  *entered* only when the page can run, (b) asserts the retry's `closed` guard through the observed
  behaviour, and (c) **C9** is new and is the regression test for the storm: a finished session plus a
  claim must settle — measured as "worker starts after close: 0, no new `phase-st`, chain stays `closed`".
* **C8b is new**: a claim on a *released* page is accepted (the operator gets `true`) but **nothing is
  started** — the case that produced the instant `Last call` death.
* **The harness was lying about time.** Its virtual clock jumped to the *farthest* pending timer on the
  first drain, so every phase after the boot ran on a page that had already hit the 120 s unclaimed
  fallback: three phases were measuring a released page rather than the revive path. The clock advance is
  now bounded, the harness claims before the window closes, its logger is a stable façade (the product
  swaps `_0xmod.log` while the stall is up, and the harness had been losing every line in between), and
  the sandbox window has the messaging surface a real page has.
* **Negative control, rebuilt:** restoring the two faults (`GoogleRelease()` on no-chores and the
  nine-slot nulling in the session `finally`) makes the suite fail **C5 and C6** again — so the checks
  now bite on the exact class of bug that shipped.
