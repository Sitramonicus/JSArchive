**Status:** measurement only. **No bytes changed, nothing rebuilt** — the 8.14 freeze
(`Working-Stable/O8.14/FROZEN-2026-09-22.md`) is untouched. This exists so a decision can be made on
numbers instead of an impression.

**Question asked:** one platform's shard (piece) is suspected of standing out from the others; can the
pieces be cross-woven so none of them pops out?

## 2. Findings

1. **The platform pockets are the best-balanced group in the pack.** Across the five `shard-p-*` pieces the
   spread is **1.75×** (128,626 – 224,490 B), z-scores run −0.94 (slack) to +1.54 (zoom), and entropy sits in
   a 0.10-wide band (6.501 – 6.596). **Discord — the one suspected — is dead centre at z = −0.02**, and the
   *largest* pocket is Zoom.
2. **The piece that actually pops out is the engine piece `shard-e1`, not a platform piece.** 440,656 B,
   **17.8% of the payload**, 2.0× the next largest, z = +3.54.
3. **The obfuscation stages compress the spread, they don't create it.** Source → shipped expansion ratios:
   zoom 17.53×, telegram 23.04×, slack 27.34×, discord 32.43×, teams 32.67×. The piece that starts biggest
   (zoom, 12,805 B at source) expands *least*; the small pockets expand most, so they converge.
4. **Piece boundaries are not textually marked.** The built bundle is a single line (0 newlines) with no
   repeated separator, and each piece ends with a different tail, so there is no marker saying "a new piece
   starts here". *(Not tested: whether a boundary-recovery heuristic — control-flow shape, identifier
   namespace changes — can still segment it. That is an open question, not a settled no.)*

## 3. Assessment of the four techniques (as proposed)

| technique | verdict for this line |
|---|---|
| 1. Cross-pollination (foreign API strings + opaque predicates) | **No.** Violates our own vocabulary rule (no platform literals on the visible surface); an unused foreign API string is a *louder* tell than a size difference; costs payload bytes we have already paid for once; a constant predicate is folded away by the first minifier in our own pipeline. |
| 2. Block-level interleave + dispatcher | **Partly already done, in the right place.** The payload's chunks are dealt into four interleaved groups inside the runner (`r3_splitR9F`, U3, dated 2026-09-21 — **present in the frozen `ad898afb` bytes**), and the g7 string tables are shattered into short blocks and interleaved (R2-03). Both interleave *data inside* a piece. Interleaving whole JS pieces with each other is not the same move: the 23 pieces share one scope and are stitched by a registry contract that our own `dangling-refs` gate enforces — splitting logic across that boundary breaks the contract the gates test. |
| 3. Size / entropy normalization | **The only one that applies, and only to `shard-e1`.** Padding is not affordable pack-wide: the carrier lands at 88.79% / 88.80% occupancy with ~62.7 KB headroom per reel, so flattening every piece to the maximum is out of budget. Entropy matching *upward* would be actively harmful — the surface is deliberately plaintext-shaped, and the codec exists to make encoded material read as plaintext. Raising entropy hands a detector the signal it wants. |
| 4. Custom virtualization | **Parked by decision (R2-04), not reopened by a generic suggestion.** A VM already exists in the line (the e3 RGF); a full custom VM moves cost from the analyst to us — build complexity, debuggability, size — against a threat model that reads rather than disassembles. |

## 4. What I would do instead, if the pop-out matters

**Rebalance the outlier, don't weave the set.** `shard-e1` is large because it carries the engine's trap
sinks plus a large share of table material. Splitting it into two sibling pieces — the same PLAN-H pattern
already validated for the `e` family (`e` → `e1`…`e4`) — would drop the maximum share from **17.8% to about
9%** and cost nothing at runtime, because the mechanism is already proven on this line. That is a build-line
change: **8.15 material, needs the operator's go-ahead.**
