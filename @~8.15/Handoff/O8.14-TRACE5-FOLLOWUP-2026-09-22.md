## 1. "Is `[OverlayRenderUtils] QUNS for Delta Force: undefined` a vulnerability for us?"

**No — and it is not ours at all.** That line is the **host client's own overlay stack**. The prefixes in
your log — `[OverlayRenderUtils]`, and the same family that shows up as the overlay starts tracking a
window — belong to the Discord client reading a *foreign process's* window state. "Delta Force" is the
game it is tracking; `QUNS` is its query against that window; `undefined` is that query coming back empty
for a process it cannot fully introspect.

Three reasons this is not actionable and not a risk to the payload:

1. **Nothing in our pieces emits `[OverlayRenderUtils]` or `QUNS`.** Our channel labels are the garden
   lexicon you anchored (Blunder, Saddlebag, Index, … Sill, Gala); the overlay strings are absent from
   every shard and from the built bytes.
2. **It fires for every tracked game, claimed or not.** It appears in your pass 1 with no session doing
   work, and it is not correlated with our claim/session lifecycle.
3. **It is upstream of us.** Whatever the overlay does with that `undefined`, it is a client-side read of
   a third-party window; our payload holds no handle to the overlay stack and passes it no data.

So: host noise, present on any game client with an overlay — the same class as the
`Error saving setting with name: console-history … exceeded the quota` line in the same trace (that one is
the client's own settings store). Nothing to handle, nothing to change.

## 2. "We still have those `[Google ]` Blanks" — fixed

**What it was.** After `GoogleRelease()` the payload wipes its packed string tables (`_pb` / `_mb`) — that
wipe is deliberate and stays: it is what makes a released page useless to a later decoder. But the channel
descriptor on every log line was decoded *per call*, after the wipe, so the decode returned an empty
string and the line printed as `[Google ] Session closed — …`.

**Fix.** The lex decoder now takes a snapshot of the 20 channel families **while the tables are alive**
(`shard-m1.js`, `_0xchSnap`), and `_0xlex.C` falls back to that snapshot whenever a live decode comes back
empty (last resort `Blunder`, never blank). The anti-decoder release is untouched — the tables still die.

**Proof (new row C11 in `tools/chain-revive-check.mjs`):** the check decodes labels, calls the real
`_wipeTables()`, decodes again, and asserts both sets are non-empty. It fails on a build with the fallback
removed, and it passes on the built pieces — i.e. it is checking the bytes that ship, not the source.

## 3. The duplicate session — `Kicked back an error: Cannot read properties of null (reading 'length')` — fixed

**What you saw.** In your pass 4: a session running, then `Ledger: 1 queued, 3 settled. next: task War
Thunder / now: Dragonheir: Chaos Revelry`, then **`Kicked back an error: Cannot read properties of null
(reading 'length')`**, then a **second** `Session closed — the ledger stands until a new claim.`

**What it was (two defects stacked).**

1. A claim arriving **while a session was already live** called the worker's `begin()` again. That started a
   *second* session loop. When the first one finished, its cleanup nulled the shared ledger — and the second
   loop then read `.length` off that null. Hence the error string, and hence a second `Session closed` line.
2. The session loop had no guard for "the ledger has gone away" — it assumed its own ledger was still there.

**Fixes.** (a) `shard-a.js`: the claim path now checks whether a session is already live
(`_liveSession` = chain `live` or started flag) and only calls `begin()` when it is not — **a claim never
starts a second session**. (b) `shard-e4.js`: the loop now stops cleanly if the ledger is gone
(`if (!Array.isArray(S._0xb)) break;`) instead of reading through it.

**Proof (new rows in `chain-revive-check`).**

| row | what it asserts | on the shipped bytes |
|---|---|---|
| `C10` | a second claim while a session is live does **not** start another worker (`begin()` call count 0, chain unchanged) | PASS |
| `C12s` | the shipping piece only loops while the ledger is an array — matched in all three build spellings (source, uglified, mound) | PASS |
| `C12` | a null ledger never surfaces as the trace-#5 TypeError or an unhandled rejection | PASS |

**Negative control (this is the part that matters).** The same three checks were run against a copy of the
pieces with exactly these fixes reverted: `C10`, `C11` and `C12s` all go **red** (11/14) while the other
eleven rows stay green — so each new check is measuring the defect it claims to, and none of them is a
tautology. Source stitch: **14/14**. Shipped pieces: **14/14**.

**Logs.** Authoritative board run on these bytes: `Active/O8.14/CC-33/reports/board-b23b.log`. The earlier
`reports/board-b23.log` is the same bytes *before* the `hold-check` tooling fix below, kept for the record.

**One tooling defect found while verifying, and fixed.** `hold-check` read the chain harness's JSON through
`execFileSync`, so a *single* red row in the harness made the whole parse fail and H4/H6/H9 reported the
runtime surface as `undefined` — i.e. the gate read "the harness had something red" as "there is no
runtime evidence". It now reads the JSON off the error object. That is why the first b23 board run showed
`hold-check FAIL (6/9)` and the second shows `PASS (9/9)` on *identical bytes*.
