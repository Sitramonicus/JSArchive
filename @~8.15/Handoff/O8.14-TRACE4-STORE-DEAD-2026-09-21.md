# O8.14 — trace #4: "why is store dead?" (corrected, 2026-09-21 late)

**Operator correction first:** **F5 is a standard page reload.** There is no "console clear" and nothing
survives the reload — the earlier "dirty page / globals survive / console-clear as a mechanism" framing
was wrong, it has been retracted in the changelog, and nothing below depends on it. `Console was cleared`
in the trace is just the reload clearing the console log.

**Question:** after a page reload (same client, no restart) a claim answers `true` while the machinery
reports `Ledger closed.` and then `[Google ] Shelf out of reach — queued chores stand, new arrivals
unwatched.` + `[Google diag] phase-n {"added":0,"storeDead":true,"totalCandidateStores":-1,
recheckWindowSeconds":15}`. Restarting the client works. *"why is store dead?"*

## Short answer

**Nothing in the venue was dead. Both lines are our own bookkeeping, and both were reporting
"my own reference is not there".**

* `storeDead` / `totalCandidateStores: -1` — the fill path counts **our** store handle (`S._0x5`). `-1`
  is not a venue count; it is "I have no usable reference". The venue was never asked and never answered.
* `Ledger closed.` — the trace shows it printed right after `await GoogleUblock('<view-slot>')`
  (the **view verb**, Pass 4 at +68.0 s and again at +514.7 s), i.e. our ledger display reading a **null**
  session ledger — which is what the end-of-session teardown writes. A *session* fact, not a shelf fact.

So the trace is one sentence: **a claim was accepted into a page whose machinery had already stood down,
and nothing in that page could start it again.**

### The reading of the diag block that misled us

`[Google diag] Host config …` / `Store check {unit: m|e|aux}` / `Pocket check {unit: pk1…pk5, apis: 6}` are
**our own payload self-checks** — our string stores and our pocket modules. They say "the script is
intact", not "the venue store was found". On a page where the machinery is dead they still print, which
is exactly how `Store check` next to `storeDead` looks like a contradiction. In this build those lines
carry `"scope": "payload"` and the venue-side state is reported by the machinery's own `chain` line
(`state`, `missing`, `ran`), so the two can no longer be confused.

### The three defects behind it

1. **One-shot scan, no retry, one-shot door.** `shard-e1.js` scans the client's module cache for the
   seven pockets and, if any is missing (the normal state for a moment after a reload), stood down;
   `shard-e2.js`'s empty-ledger path did the same *before* it published `_0xch`/`pk38`, which is exactly
   what `shard-e4.js`'s boot check needs to start the worker. So the only door to a working session was
   welded shut by a page that scanned a few seconds too early.
2. **The claim path was independent of the chain.** `shard-a.js` accepts a claim and returns `true`; it
   never asked whether anything was behind it, and it could not start anything.
3. **The teardown threw away our own references.** At the end of a session `shard-e4.js`'s `finally`
   nulled `S._0x1 … S._0x9` (the chunk array, the require function and the seven venue handles) and
   `S._0xb`. After that, every later call read a null handle and blamed the shelf — the `-1`.

## What the fix does (build 20)

* **The chain is a named state machine**: `scanned → … → waiting-pockets / waiting-capability /
  waiting-chores / armed / live / closed`. A cold page is a *wait*, never a silent stop.
* **`_0xarm()`** (e1) re-scans and re-evaluates; it also publishes `_0xpocketsMissing` (`c3…c9`), so a
  claim can say *what* it is waiting for.
* **`_0xseed`** (e2) and **`begin`** (e4) are published, so a page that never armed can still be started.
* **The claim drives the revival**: an accepted claim sets `S._0xclaimed`, re-arms, and calls `begin()` —
  and **reports** `[Google diag] chain {state, ok, missing, ran, revived:true}` so a debugger can see at
  a glance whether the session has a worker behind it. (`ran` = a session actually reached the shelf on
  this page.)
* **Late-arm retry with a claimed slow tail**: 30 fast ticks (5 s) then a slow tail (15 s) — but only
  while a claim is present, so the anti-decoder property is untouched: no claim, no work, whatever the
  venue does.
* **The teardown keeps the captured references** and clears only *session* state (`_0xb`, `_0xledger`,
  `_0xstarted`, chain → `closed`). A later `<res-slot>` reads the real shelf instead of a null handle.
* **The worker's chain state is visible from the outside**: `live` while it runs, `closed` when a
  session ends, `waiting-*` when it is waiting for the venue — and the claim reports which one it is.
* **Diags that no longer lie**: `storeDead` is now true only for a genuine shape problem; the line carries
  `storeHandle: "not-loaded" | "unexpected-shape"`, the real candidate count (`_0list.length`, i.e. `0`
  here — printed as `0`, not `-1`), `chain`, and `pocketsMissing`. `Ledger closed.` is only said when a
  session really ran and ended; otherwise it says the shelf was never reached on this page.

## What the operator asked for in the same trace (all now implemented)

Three asks sit in the comments of this log; the first pass over it recorded none of them.

1. **"what if: pwdDbg has the capacity to reignite the dead flames (… like a jump starter) — I know it
   isn't implemented yet (yes, let's add it)"** → `_0xrevive()` runs on **both** accepted branches of the
   entry point (the gate accepts either hash; the level-2 branch and the error path call it too), so a
   `pwdDbg` claim restarts a dead page exactly like `pwdRcd`. **Verified by C8**, which drives the shipped
   entry function at level 1 *and* level 2 and asserts the arm + begin side effects.
2. **"maybe add a warning to restart client? (only if this console refresh can't be resolved)"** → a
   **one-shot** line, printed only after the fast retry window is spent **and** only while a claim is
   waiting: `Shelf still out of reach — waiting on <pockets>. If this session does not start on its own,
   restarting the client is the reliable workaround.` Claim-gated, so an unclaimed/decoder page never sees
   it.
3. **"I want to know whether upgrading to log level 2 will fix it for now"** → answered by the trace
   (it did not) and by the code: nothing in the chain was level-gated, so verbosity could never have
   repaired it. Level 2 now carries the jump-starter above, because a level-2 claim takes the same revive
   path.

Also confirmed from the trace: `await GoogleUblock('NotAPwd')` → `false` with **no** garden fallback — the
operator's own check that a wrong passphrase is not a decoder tell. Unchanged in this build.

## Corrections to my own earlier write-up

* **Retracted: "the `F5 whilst in console` line was never in the shipped build-18 bytes."** It was in the
  **source** that built build 18 and I removed it during build 19; the claim that it was never shipped
  rested on a byte grep for English text, and **the shipped payload contains no readable English at all**
  — message text is char-code encoded into lex tables (`Shelf out of reach`, `Ledger closed.` and
  `Welcome back` are all ungrepable). Byte greps for English in this payload prove nothing; only the
  runtime/decoded surface counts. What is true: no trace shows that line printing, because on those pages
  no session ever reached its end.
* **Refined:** `Ledger closed.` came from the **view verb** on a page where no session had ever reached
  the shelf — see the Short answer above.

## Residual / not over-claimed

* The end-of-session `finally` only runs against a live venue, so C6 pairs a runtime identity guard with a
  static check on the piece.
* If the venue's modules never register at all, the page stays in a named waiting state and stands down —
  it does not pretend to work and does not block a later paste. The claim's `chain` line makes that
  visible instead of silent.
