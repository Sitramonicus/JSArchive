## A. The label regression — real, and now fixed

**Symptom:** every normal-operation line came out stamped but untagged:
`[06:21:50.049 +0.5s] 1 chore pinned to the board for this shift.`

**Cause:** `Log.say` painted the channel tag only while the debug gate was open —
`(会員 >= 2 && _0xopen) ? ['[Google ' + … + ']', m] : [m]` — and `_0xopen` starts `false`
(`shards/shard-a.js:4`) and is only set true on the debug-gate path (`:114`, `:123`, `:124`). So the
tags you remembered (`[G:Comic]`, `[G:Discord]`, …) were from **debug runs**, where the gate was open;
in normal operation the tag was silently dropped and the new stamp took its place in front of the
message. Nothing was deleted — but from the console it is indistinguishable from "the timestamp
replaced my label", which is exactly how you read it.

**Fix:** the tag is **unconditional** (`会員 === 0` still silences the whole sink — that knob returns
the noop set). Tags also show whole words now: a plain channel word passes through in full
(`[Google Allotment]`, `[Google Discord]`); only an opaque-looking token is clipped to 8 — the first
cut clipped everything and produced `[Google Allotmen]`, which reads like a defect.

**Two emitters we own also bypassed the stamped sink entirely and were fixed in the same pass:**

| emitter | before | after |
|---|---|---|
| `shards/shard-m1.js` `MemberCount.report()` | raw `console.debug` → `[MemberCount] No member statistics are currently available in local client state.` with **no stamp** | routed through the sink → `[HH:MM:SS.mmm +Ns] [MemberCount] …` |
| `shards/shard-aux2.js` `rehearseLedger()` | 12 decoded `[Google ledger\|relay\|tile\|route\|echo …]` lines straight to `console.debug`, **no stamp** — the burst that reads as "logs that could be related to us" | routed through the sink → all 12 stamped |

Verified in the build trace: `[22:35:31.175 +0.0s] [Host 8.14] initialized …` and
`[02:35:31.604 +0.4s] [Google Hothouse] Nothing ripe on the trees today …` — tag and stamp together.

## B. The CSP alerts — not ours, and nothing is being blocked

**Measured, not argued:** `tools/netwatch-probe.mjs` (new) runs the shipped payload in the same
Discord-faithful sandbox as `fullwire-probe.mjs`, except every network-capable API is a counting trap —
`fetch`, `XMLHttpRequest` (open/send), `WebSocket`, `EventSource`, `Worker`, `SharedWorker`,
`RTCPeerConnection`, `navigator.sendBeacon`, `Image.src`, `Audio`. Result on the shipped bytes:

```
after init:                 network-primitive calls=0  {}
after GoogleUblock(pwdDbg): network-primitive calls=0  {}
                            no URLs attempted
```

**Your own trace names the source:** `[RTCLatencyTestManager] RTC region latency test completed,
ranked regions are: (5) ['singapore','japan','hongkong','india','sydney']` — the client's own
connectivity test — plus `Creating a worker from 'https://discord.com/assets/fd640ecc3f512e29.js'`
(Discord's own asset) and `[Violation] 'focus' handler took 166ms` (a page performance advisory).

**And the policy is report-only:** every line ends *"The policy is report-only, so the violation has
been logged but no further action has been taken."* Nothing is blocked; these are advisory reports the
client emits about its own activity. `Connecting to '<URL>'` / `''` is Chromium reporting with a
redacted URL, not a request from our code.

**One honest nuance:** our synthetic running-game records *do* make the page's own subsystems react —
the trace shows `[Clips] decider: handleRunningGamesChange …`, `[OverlayRenderStore] Tracking game
42658 for overlay`, `[OverlayRenderUtils] QUNS for Delta Force`, `Overlay method for pid 42658
"Delta Force" to Disabled`. That is the restored r3 mechanism **working**: the client believes a game
is running. Those reactions are the page's; any connection attempt among them is the page's own
connectivity behaviour, not code we ship.
