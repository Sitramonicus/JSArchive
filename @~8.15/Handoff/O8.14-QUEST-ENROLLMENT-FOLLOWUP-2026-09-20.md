## Interpretation

1. **The mechanism works.** Enrolment, pacing, progress reporting, and delivery all functioned: one
   chore went 5/29 → 29/29 and was reported delivered. Nothing here is a decode/gate/venue fault.
2. **The gap is policy, not mechanics.** Of 77–78 candidate items, **51–52 are skipped as
   `unenrolled`** and 22 as `settled`. "Unenrolled" means the item's *type* is not in the set this
   build elects to work. Only video-type items are in that set today, which is exactly the operator's
   observation: only video chores progressed.
3. `[G:Chart] 2 set aside — shape we can't take on` / `2 left off — shape we can't fold today` are the
   intra-set skips (shape/types the enrolled code path cannot fold), separate from the type filter.
4. `[G:Dial] Grains landing whole: false` plus the growing `decimals` in `phase-t` ticks is the string
   layer's timing jitter report, not an error; it is worth keeping an eye on across runs.

## Do we have tests for this? — honest answer

We have tests for **mechanism**, not for **policy coverage**:

| test | what it covers | why it cannot see this |
|---|---|---|
| matrix 24 / tiers 42 | carrier decode, tiers, degradation paths | fixture payloads, not real quest shapes |
| leakcensus / detector / coverage / parity | bytes and vocabulary | no notion of candidate types |
| split-equivalence | piece splits behave identically | mock host, synthetic candidates |
| full-wire venue probe | the assembly runs at all in a Discord-like host | mock host has no candidate distribution |

Nothing offline knows the *distribution of candidate types in a real client*, so no test could assert
"this chore type is enrolled". That is the actual gap, and the trace supplies the missing data.

## Proposed course (no action taken yet)

1. **Freeze this trace as a fixture** — `tools/quest-enroll-replay.mjs` fed with the observed counts
   (`unenrolled 51…52`, `settled 22`, `wrap 2`, `seen 1`, `queued 1`, total 77–78) and a small table of
   candidate shapes, asserting: video type → enrolled and fully progressed; non-video types → skipped
   with the *expected* reason. This turns the current behaviour into a regression test, so a later
   widening cannot silently regress the video path.
2. **Widen enrolment only if it is the goal.** Deliberate costs: (a) more API surface touched per run
   (each type needs its own harvest/progress shape, which is a real leak-surface increase);
   (b) more console fiction, which raises the cost of a human reading the trace; (c) if a non-video
   path is implemented badly it produces exactly the class of fault we just fixed (an error-path
   ReferenceError). Recommended: widen one type at a time, behind the fixture, with the run reporting
   the new type's success count.
3. **Do not chase the `settled: 22`** — those are genuinely already-done items; skipping them is right.

## Concern to state plainly

As long as the enrolment set is video-only, the operator's headline metric ("did my quest progress?")
will keep reading as a partial success even when the payload is perfectly healthy. If the live-test
target is *that* quest, we should confirm its type first (one line in the trace names it: the quest
being worked appears as `Invincible: Guarding the Globe`, so video). If their target is a different
quest, the fix is policy widening, not debugging.
