## The bare `false` at +0.3 s

**No code path of ours prints a bare boolean** — the console sink only ever writes tagged lines
(`[Host …]`, `[MemberCount] …`, `[Google …]`) or the garden; a bare `false` is a console *completion
value* (the value of an evaluated expression), not one of our lines. Two candidates, both harmless:

* **You typed a call.** A `GoogleUblock(…)` with a mis-typed or placeholder argument answers `false` —
  that is the gate's honest answer, and note the placeholder string `pwdDbg` is *not* a slot value; the
  values exist only in your `pwdRcd…pwdView` map. A wrong or late attempt never burns the window: a
  correct value inside the two minutes still opens the session.
* **The paste's own completion value**, echoed by that console.

One related fact from the build, worth knowing because it explains the silence: the machinery runs a
self-test at boot that calls its own entry point with the staff name (the string layer composes
`GoogleUblock` from char codes at that call site) and gets `false` back — bootstrap, not a claim. That
call does not print; the gate simply answers false for anything that is not a slot value.

Not changed, because it is cosmetic and I would rather you confirm the reading first: if you want the
completion value silenced, it is a one-line change in the payload's self-test (drop the `await`/store
it) and it can ride the next build.

## Defect 1 (fixed): a claim through `GoogleUblock` did not lift the stall

Wiring the service-side hold made this visible, and the new gate **S11** proves it. The entry point is
defined **outside** the closure that owns the stall flag, so its `_0xstall = false` did not touch that
binding — in sloppy mode it created a *global* instead, in strict mode it would have thrown. Effect on
build 16: `GoogleUblock(pwdRcd)` answered `true`, while the console stayed stalled (no tags, no
machinery) **and** no garden appeared at the window's end, because the claim had suppressed the
fallback. That is the worst of both worlds — exactly the silent machine you warned about.

Fixed: the closure publishes `_0xmod._stallLift()` and every claim path calls it. S11 asserts the four
states — unclaimed → held, in-window claim → free, pre-set claim → free, window over → held — and that
no global leaks. Pre-set claims (`名` edited before sending) were never affected: that path runs
*inside* the closure and always worked.
